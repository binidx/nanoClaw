# 国际化（i18n）

本文描述 NanoClaw 当前的国际化实现、语言切换方式，以及后续新增语言的操作流程。

## 当前状态

- 当前已支持两种语言：
  - `zh`
  - `en`
- 前端和后端都已接入独立的 i18n 资源。
- 前端会自动把当前语言通过 `X-Locale` 请求头传给后端。
- 后端会优先读取 `X-Locale`，其次读取 `Accept-Language`，默认回退到 `zh`。

## 用户如何切换语言

### Web 控制台

- 左侧导航栏底部有语言切换按钮：
  - 当前是中文时显示 `EN`
  - 当前是英文时显示 `中`
- 切换逻辑在：
  - `web/src/components/NavSidebar.tsx`

### 持久化方式

- 当前语言会保存到浏览器本地存储：
  - key: `nanoclaw_locale`
- 语言检测顺序：
  1. `localStorage.nanoclaw_locale`
  2. 浏览器 `navigator.language`
  3. 默认回退 `zh`

### 前后端联动

- 前端 i18n 初始化文件：
  - `web/src/i18n/index.ts`
- 后端 i18n 初始化文件：
  - `src/i18n/index.ts`
- 后端 locale middleware：
  - `src/i18n/middleware.ts`

## 目录结构

### 前端

前端语言资源位于：

```text
web/src/i18n/locales/
  zh/
  en/
```

每个目录按 namespace 拆分，例如：

- `common.json`
- `nav.json`
- `chat.json`
- `settings.json`
- `assistants.json`
- `knowledge.json`
- `repoReview.json`

### 后端

后端语言资源位于：

```text
src/i18n/locales/
  zh/
  en/
```

当前后端 namespace 包括：

- `errors`
- `doctor`
- `onboard`
- `config`
- `permissions`
- `repoReview`
- `stock`
- `soul`
- `knowledge`
- `prompts`
- `channels`
- `workteam`
- `slashCommands`

## 如何新增一种语言

下面以新增 `ja` 为例。

### 1. 新增前端 locale 目录

创建：

```text
web/src/i18n/locales/ja/
```

把现有 `zh` 或 `en` 下所有 namespace 文件复制过去，再逐个翻译 value。

至少应覆盖当前前端已注册的 namespace：

- `common`
- `nav`
- `chat`
- `settings`
- `knowledge`
- `assistants`
- `soul`
- `tasks`
- `users`
- `workteam`
- `stock`
- `channels`
- `apps`
- `repoReview`
- `errors`
- `im`
- `codeMap`
- `live2d`
- `subagent`
- `share`
- `terminal`
- `approval`
- `browser`

### 2. 在前端注册新语言

修改：

- `web/src/i18n/index.ts`

需要做三件事：

1. 引入 `ja` 的各 namespace JSON
2. 在 `resources` 中新增 `ja`
3. 如果需要，把 UI 语言切换逻辑从二选一改为多选

当前 `NavSidebar.tsx` 的切换逻辑是：

- `zh <-> en`

如果新增第三种语言，建议改成：

- 下拉选择
- 或循环切换

### 3. 新增后端 locale 目录

创建：

```text
src/i18n/locales/ja/
```

同样按现有 namespace 建立 JSON 文件，并补齐翻译。

### 4. 在后端注册新语言

修改：

- `src/i18n/index.ts`

需要做三件事：

1. 引入 `ja` 的各 backend namespace JSON
2. 在 `resources` 中新增 `ja`
3. 放宽 `getLocaleFromReq()` 对语言值的判断

当前 `getLocaleFromReq()` 只接受：

- `zh`
- `en`

新增语言后，需要把判断扩展到新语言代码。

### 5. 检查前后端请求链路

前端会自动注入：

- `X-Locale`

一般不需要改请求调用点；只要前端 `i18n.language` 能切到新语言，后端就会收到对应 header。

### 6. 补齐测试和验证

新增语言后，至少应验证：

- 前端 `npm run build`
- 根目录 `npm run build:all`
- 关键接口返回不再泄漏原始 key
- 语言切换后：
  - 聊天页
  - 设置页
  - Assistants
  - Knowledge
  - Repo Review
  - IM
  页面没有明显中文/英文串场

## 开发约定

### 1. 优先复用现有 namespace

不要随意新增碎片化 namespace。优先把文案放进已有主题文件。

### 2. 优先使用稳定 key

新代码尽量使用可读、稳定的 key，例如：

- `chat.send`
- `assistants.secret.save`

避免继续扩大：

- 中文直接做 key
- `auto.xxxxxxxx`

但已有存量 key 可以保守兼容，不要求一次性全量重构。

### 3. 前端与后端的职责

- 前端负责：
  - 页面文案
  - 交互控件
  - 占位符
  - 本地提示
- 后端负责：
  - API 错误消息
  - 运行时用户可见提示
  - slash command 输出
  - 文件导入/安装/校验类报错

### 4. 不需要翻译的内容

通常不纳入 i18n：

- 测试样例里的中文文本
- 识别中文输入的正则
- 知识库内容本身
- 用户上传文档正文
- 业务数据字段值本身

## 关键文件

- 前端入口：`web/src/i18n/index.ts`
- 后端入口：`src/i18n/index.ts`
- 后端 middleware：`src/i18n/middleware.ts`
- 语言切换按钮：`web/src/components/NavSidebar.tsx`

## 当前限制

- 语言切换 UI 目前是 `zh/en` 二选一，不是通用多语言选择器。
- 后端仍保留一部分历史 key 风格，新增语言时需要优先补齐实际命中的 key。
- 还没有自动化“locale key 对齐检查”，目前主要依赖构建和页面验证。
