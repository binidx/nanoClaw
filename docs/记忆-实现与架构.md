# 记忆-实现与架构

## 这份文档解决什么问题

NanoClaw 的 Memory 不是“把聊天记录存下来，下次一起喂给模型”。当前实现把会话上下文、durable memory、identity、压缩摘要、搜索索引、recall 事件和观测拆成多层数据，再在运行时按预算重新装配进 prompt。

这份文档只描述当前仓库已经落地的实现，不描述未来路线。

## 总体分层

### 1. `context_entries`

会话级上下文层，解决“当前这轮模型该看到什么”。它记录的不是最终 transcript，而是后续轮次可能需要重新引用的上下文片段。

当前常见 `source_type` 包括：

- `chat_message`
- `assistant_message`
- `memory_recall`
- `compaction_summary`
- `post_compaction_context`
- `memory_promotion`

### 2. `user_memories`

长期用户记忆源头，解决“哪些用户事实、偏好和长期规则已经被系统确认”。它承载：

- 显式 `remember` 写入的用户长期记忆
- observations 经 consolidation 提升后的 durable/core memory
- Soul prompt 使用的核心记忆、偏好、人格相关记忆

默认读取 `timeScope='current'` 会过滤 `valid_from` / `valid_to` 和 `expires_at`。其中 `valid_from` / `valid_to` 表示事实本身的有效期，`expires_at` 表示系统保留/淘汰期。

### 3. `memory_documents`

检索投影层，解决“哪些 durable source 可被运行时搜索召回”。它承载：

- `memory_file`
  来自 `MEMORY.md` 和 `memory/**/*.md`
- `identity_memory`
  来自人物主档物化出的 identity markdown
- `user_memory`
  来自 `user_memories` 的自动投影
- `compaction_summary`
  作为可搜索文档进入索引链路的摘要类条目

`memory_documents` 不是普通用户长期记忆的事实源；手动记忆和自动沉淀应先写 `user_memories`，再同步投影到 `memory_documents`。

### 4. `conversation_identity_bindings`

会话到 person 的绑定层，解决“这是谁的长期信息”。identity memory 之所以不是普通 group memory，核心就在这里。

### 5. `context_compactions`

长历史压缩层，解决“长对话如何不把 prompt 撑爆”。它把较旧聊天片段变成摘要，而不是无限回放原文。

### 6. `memory_events`（Raw Ledger）

审计日志层，解决"每一条记忆经历了什么"。记录 ADD / UPDATE / DELETE / MERGE / EVICT / PROMOTE / SKIP / RECALL 八种事件，每个事件携带 before/after 快照和 decision_reason。

`user_memories.source_event_id` 反向指向触发创建该记忆的 ledger 事件 ID，构成 provenance 链。

### 7. `memory_skills`（Procedural Memory）

技能记忆层，解决"可复用的操作流程如何持久化"。表结构包含 trigger_pattern、body、termination_condition、success/failure 计数。当前有完整 CRUD 接口但运行时尚未集成。

### 8. `user_memories` 的 bi-temporal 字段

`valid_from` / `valid_to` 支持事实时间切片查询，`expires_at` 支持系统保留/淘汰查询。默认 `timeScope='current'` 时自动过滤未来生效、事实失效或系统过期的记忆，`timeScope='all'` 返回全量。该机制覆盖 `getUserMemories`、`getUserCoreMemories`、`searchUserMemories`（包括 LIKE fallback）。

### 9. `memory_*_stats`

观测层，解决“系统现在到底怎么运行”。它统计配置、生效状态、搜索、新鲜度、promotion、prompt 预算等快照。

## 为什么不是简单聊天记录回放

如果只按时间顺序回放消息，会有几个问题：

- 长会话 prompt 无限增长
- durable fact 和一次性闲聊没有区分
- identity、group memory、global memory 无法按语义优先级进入上下文
- 已压缩内容会和原文重复进入 prompt
- 搜索读到的片段无法在后续轮次里稳定复用

当前实现因此采用“当前轮消息 + 近期上下文 + durable recall + compaction summary”的分层装配，而不是消息表全量回放。

## 运行时主数据流

### 用户消息进入时

用户消息进入后，系统不会只写 `messages`。当前实现还会：

1. 写入会话相关的 `context_entries`
2. 对显式 `remember` 直接写 `user_memories` 并同步 `user_memory` 检索投影
3. 尝试对高信号用户表达做 observation / promotion 判断
4. 为当前 `chat_jid` 调度 compaction job

即时 promotion 只聚焦用户聊天消息，不会把所有运行时中间态都当作 durable memory 候选。低置信 observations 默认只供 Soul 页面和 consolidation 使用，不直接注入 prompt。

### 助手回复落库时

助手回复落库后，也会补充对应的 `context_entries`，并再次调度 compaction。这样后续轮次装配 prompt 时，既能看到近期用户意图，也能看到最近助手已经承诺或解释过的内容。

### 真正调用 Agent 前

运行时会在 `buildAgentPromptInput(...)` 中调用 `assembleAgentContext(...)`，把以下内容拼成实际输入：

- 当前轮 `sourceMessages`
- 近期会话上下文
- durable memory recall 结果
- 最新可用的 compaction summary

最终不是直接拼整段历史，而是先形成 `<recent_context>...</recent_context>`，再拼当前轮 `<messages>...</messages>`。

## Prompt 装配规则

### 当前轮消息始终单独保留

本轮 `sourceMessages` 始终独立参与 prompt 组装，不依赖 `context_entries` 回捞。这样可以避免当前轮消息遗漏，或既来自实时输入又来自历史候选而重复注入。

### 近期上下文来自 `context_entries`

历史候选主要来自 `getContextEntries(chatJid, N)`，但进入 prompt 前会做过滤：

- 当前轮消息对应 entry 会被过滤掉
- 不在 prompt 白名单里的 `source_type` 不会进入
- 如果已有 compaction summary，被其覆盖的旧 entry 会被排除

当前主要允许进入 prompt 的是：

- `chat_message`
- `assistant_message`
- `compaction_summary`
- `memory_recall`
- `post_compaction_context`

`assistant_turn` 虽然单独持久化，但不属于这层 prompt 注入白名单。

### durable recall 不是扫全量聊天

当前 recall 的流程是：

1. 从最近 2 条 `sourceMessages` 提取查询文本
2. 用 query 去搜 `memory_documents`
3. 按 scope、owner、source type 和用户记忆有效期过滤结果
4. 把命中的片段写回 `memory_recall` 类型的 `context_entries`
5. 实际注入 prompt 的 durable recall 写 `memory_events.RECALL`
6. 后续装配时再把这些 recall entry 当作会话级上下文的一部分

因此 durable memory 的主语义来自文档和 identity，而不是消息历史。

### identity memory 的优先级

如果当前 conversation 绑定了 person，runtime 会优先把 identity memory 纳入 recall 搜索。group/global durable memory 会在此基础上继续参与排序。

这意味着：

- identity memory 是人物层长期事实
- group/global memory 是环境层长期事实

## Prompt 预算控制

预算控制来自 `getMemoryContextConfig()`。

### 1. snippet 数量上限

默认首先受 snippet 数量约束，而不是 token 精算。实现里既有代码默认上限，也可以通过 `MEMORY_PROMPT_MAX_SNIPPETS` 调整。

### 2. token budget

只有 `MEMORY_PROMPT_TOKEN_BUDGET > 0` 时，runtime 才会按 token 预算分桶；否则主要按 snippet 上限控制。

### 3. 三类预算分桶

开启 token budget 后，当前实现会按三类来源分配预算：

- `recent`
- `summary`
- `recall`

默认比例由这些配置控制：

- `MEMORY_PROMPT_RECENT_RATIO`
- `MEMORY_PROMPT_SUMMARY_RATIO`
- `MEMORY_PROMPT_RECALL_RATIO`

未被某一类用完的预算会释放成 carry budget，供其他桶继续消费。

### 4. 单条内容截断

即使 entry 被选入 prompt，也还会做单条内容截断：

- 普通 prompt context 约 600 字符
- `memory_recall` 约 800 字符

因此“命中了 recall”不等于“整篇文档全文进入模型”。

## identity、文档索引与搜索

## identity 三层模型

当前 identity 不是单表设计，而是三层结构：

- `person_profiles`
  人物主档
- `identity_aliases`
  人物别名与渠道映射
- `conversation_identity_bindings`
  会话到人物的绑定

`src/memory/identity-service.ts` 的职责不是存储，而是把输入规范化为稳定键：

- `displayName` 必填
- `personId` 会被 slug 化为小写、只保留字母数字和 `-`
- ID 最大长度 64
- `notes` 去重
- `aliases` 归一化并去重

## identity 文档物化

identity 不只存在于数据库，也会物化成全局 memory 文档：

- 相对路径：`memory/identity/{personId}.md`
- `path_ref`：`global:memory/identity/{personId}.md`
- `doc_id`：`identity-memory:{personId}`
- `scope`：`global`
- `owner_type`：`person`
- `owner_id`：`{personId}`
- `source_type`：`identity_memory`

这里要特别注意：identity 文档虽然是 `global` scope，但 owner 是 `person`。说明 `scope` 和 `owner` 是两个不同维度。

## 普通 memory file 的扫描范围

普通 memory 文档扫描范围是显式限定的：

- 允许 `MEMORY.md`
- 允许 `memory/**/*.md`
- 显式排除 `memory/identity/**`

排除 identity 目录的原因是 identity 文档已经由独立链路物化，不能再被文件扫描链路重复索引。

## `scope`、`owner`、`source_type`

### `scope`

表示文档在哪个检索可见域里：

- `group`
- `global`

### `owner_type + owner_id`

表示文档真正归属给谁：

- `group + {groupFolder}`
- `global + global`
- `global + {userId}` for `user_memory` projections
- `person + {personId}`

### `source_type`

表示文档来自哪条链路。当前检索侧最重要的是：

- `memory_file`
- `identity_memory`
- `user_memory`
- `compaction_summary`

不要把这些来源都混成同一类“长期记忆文件”。其中 `user_memory` 是 `user_memories` 的检索投影，`memory_file` 是外部手写知识入口。

## 增量同步状态

文件侧同步依赖 `memory_document_sync_state`，而不是每次全量重建。关键字段包括：

- `path_ref`
- `scope`
- `owner_type`
- `owner_id`
- `source_type`
- `file_mtime_ms`
- `file_size`
- `content_hash`
- `last_synced_at`

它的职责是记录文件侧 freshness，不是搜索索引本身。

## 文件同步链路

普通 memory file 的同步流程大致是：

1. 枚举允许路径
2. 生成稳定 `path_ref`
3. 读取现有 sync state
4. 先用 `mtime + size` 做快速跳过
5. 如有必要再读正文并计算 `content_hash`
6. upsert `memory_documents`
7. 同步更新 FTS / search index
8. 写回 sync state

这是一套“高效优先”的增量策略，不是每次全量校验。

## 搜索分层与排序

上层会话搜索顺序是：

1. 如果 conversation 绑定了 person，先搜 `identity_memory`
2. 再按 scope 搜 group memory file
3. 再按 scope 搜 global memory file
4. 去重后统一排序并截断

底层搜索走 `searchMemoryDocuments(...)` 和 `searchMemorySearchIndex(...)`。当前支持 hybrid 检索模式：BM25 + vector embedding（cosine similarity）混合打分。当 embedding provider 可用时，memory document 索引时会自动生成 vector embedding（owner_type=`memory_doc`），召回时按 `VECTOR_ALPHA=0.3` 加权合并向量分与 BM25 分。不可用时自动退化为纯 BM25。

最终排序叠加：

- hybrid score（BM25 + vector 加权）
- temporal decay（半衰期 30 天的指数衰减）
- token coverage
- exact match boost
- recency boost
- source boost

默认 source boost 的倾向是：

- `identity_memory` 更高
- `memory_file` 基准
- `compaction_summary` 更低

## substring fallback 与多方言支持

FTS 对 CJK 和极短查询并不总是稳定，因此当前实现会在这些场景启用 substring fallback：

- 查询包含 CJK
- 查询 token 很少，接近单词级

它不是为了替代 FTS，而是避免中文或短词查询时出现“文档里有但 FTS 没命中”。

searchMemoryDocuments 在 SQLite 上使用 FTS5，MySQL/PostgreSQL 上使用 LIKE fallback，三套方言均可用。searchUserMemories 同样在 PG 上使用 	o_tsvector，MySQL 上使用 MATCH AGAINST，失败后统一回退到 LIKE。所有路径都对 bi-temporal 字段做过滤。

## snippet 与 recall 的关系

`search-snippets.ts` 会从正文中选出最佳命中行，返回带行号的摘录。这解决的是展示问题。

而 `memory_recall` 解决的是运行时问题：某段命中的记忆是否真正写入当前会话上下文。

因此：

- snippet 面向展示
- recall 面向运行时注入

## 压缩、提升与显式记忆动作

## 压缩为什么存在

如果把聊天历史全部原样塞回 prompt，会出现：

1. prompt 长度不可控
2. 模型反复看到过旧上下文噪声
3. durable 线索和普通对话混在一起

因此当前实现把“近期原文”和“较早历史摘要”分开管理。

## 压缩调度与执行

当前 compaction 是“事件触发入队 + 后台异步执行”，不是同步串在本次回复里。

触发时机：

- 新用户消息写入 `context_entries` 后
- 助手回复写入 `context_entries` 后

后台 loop 的关键约束：

- 单次最多处理 20 个 job
- 执行前先 claim，避免并发重复跑同一会话
- 失败后 30 秒退避重试

它是 per-chat 去重队列，不是每条消息一个独立压缩任务。

## 压缩对象与阈值

当前压缩主要针对：

- `chat_message`
- `assistant_message`

不会把所有 memory-related entry 都重新压成摘要。

只有当 eligible entries 超过 `MEMORY_COMPACTION_TRIGGER_ENTRIES` 时，才会真正生成 compaction summary。最近若干条原文会通过 `MEMORY_COMPACTION_KEEP_RECENT_ENTRIES` 保留不压缩。

## 压缩产物

压缩完成后会写入：

- `context_compactions`
- `context_compaction_jobs`
- `context_compaction_run_logs`

summary 的核心目的是：

- 在 prompt 装配时替代旧原文
- 为后续 durable candidate 提取提供稳定输入
- 在排障时让人看见“系统到底压缩了什么”

## Promotion 的职责

Promotion 不是“把任何一句话都写进长期记忆”。它做的是：

1. 把用户表达分类成更稳定的记忆语义
2. 决定应该落到哪里，或者根本不落 durable memory

当前常见分类包括：

- `identity`
- `group_durable`
- `global_durable`
- `session`
- `ttl_task`
- `none`

## 即时 Promotion

`autoPromoteMemoryFromEntries(...)` 只看：

- `role=user`
- `source_type=chat_message`

处理顺序大致是：

1. 从新用户消息中提取 durable candidate
2. 先记一条 `candidate` 类型 ledger
3. 再根据配置决定是否真正写入 durable memory

## 显式 `remember` 与 `session_only`

会话里显式记忆动作走的是 API：

- `remember`
  直接走 durable memory 写入路径
- `session_only`
  只写一条会话级 memory entry，不写 durable memory 文件

因此：

- `remember` 是长期记忆写入请求
- `session_only` 是当前会话的上下文增强

## Durable Memory 的落点

普通 durable note 默认写入 daily memory 文件：

- `group:memory/YYYY-MM-DD.md`
- `global:memory/YYYY-MM-DD.md`

写入时会做去重。

如果 candidate 被识别为 `identity`，则会：

1. 创建或更新 person profile
2. 合并 alias
3. 绑定当前 conversation 到 person
4. 投影到 `global:memory/identity/<personId>.md`

`global_durable` 只有开启全局写开关后才会真正进 global，否则会退回 group daily memory。

当前 compaction 后若开启 auto-save，会把旧上下文里提取出的 durable candidates 批量写入 group-scope memory。它更接近“沉淀组级 durable note”，不是完整的 identity/global 精准重分类流水线。

## 观测与指标口径

当前 Memory 观测主要来自：

- `/api/memory/status`
- `/api/status` 里的 memory 快照

返回内容会聚合为：

- `config`
- `ledger`
- `compaction`
- `promotion`
- `identity`
- `search`
- `prompt`

### `ledger`

`ledger` 统计 `context_entries` 层面的总体情况，例如总 entry 数、24 小时内新增 entry 数、按 `source_type` 分组的 entry 数。它反映的是上下文账本规模，不等于 durable memory 文档规模。

### `compaction`

`compaction` 看两类信息：

- 摘要侧：`totalCompactions`、`recentCompactions24h`、最新 summary
- worker 侧：`pendingJobs`、`runningJobs`、`recentRuns24h`、`recentFailures24h`、平均耗时、最近成功/失败时间

### `promotion`

要分开理解：

- `candidates24h`
- `writes24h`
- `deduped24h`

它们是事件口径，不是同一批唯一对象的状态迁移计数。

另外还有：

- `byAction24h`
  `auto / remember / session_only`
- `byOrigin24h`
  候选来自哪里
- `byMemoryClass24h`
  `identity / global_durable / group_durable / session / unknown`

### `identity`

当前更适合看：

- `totalProfiles`
- `boundConversations`
- `aliases`

### `search`

常用口径包括：

- `indexedDocuments`
- `syncStateDocuments`
- `indexedHitCount24h`
- `indexedResultCount24h`
- `searchFollowupReadCount24h`
- `followupReadRate24h`
- `fallbackSyncCount24h`
- `freshnessRecheckCount24h`
- `staleRefreshCount24h`
- `filesSynced24h`
- `filesSkipped24h`
- `filesDeleted24h`

`followupReadRate24h` 更接近“检索结果是否被继续使用”的代理指标，不是答案正确率。

### `prompt`

常见值包括：

- `lastAssembledTokenEstimate`
- `lastRecentTokens`
- `lastSummaryTokens`
- `lastRecallTokens`

它们只反映最近一次记忆注入的预算分配，不是长期平均值。

## 延迟来源与能力边界

### 延迟来源一：Compaction 是异步轮询

消息写入后只是入队，不会同步等待压缩完成。入队后还要等 poll interval；失败时还会退避重试。

### 延迟来源二：文件索引和搜索不是强实时

promotion 写入 daily memory 文件后，搜索可见性还依赖：

- 文件同步 loop
- fallback sync
- freshness recheck / stale refresh

因此“文件已写入”不等于“下一次搜索一定立刻命中”。

### 关键边界

- 记忆不是全量聊天历史自动注入
- 不是所有记忆都来自数据库
- searchable 不等于 auto-injected
- `session_only` 不是 durable memory
- 自动 promotion 更接近规则驱动的高信号捕获，不是通用语义理解器
- 不是所有来源都会自动升格，当前自动链路聚焦用户聊天消息

## 常见误解

- Memory 不等于聊天历史
- 所有记忆不会自动注入
- identity/group/global 不是展示标签，而是运行时语义
- 搜不到不一定是系统忘了，也可能是 scope、owner、同步时延或预算问题
- `deduped` 不等于失败
- `followupReadRate` 不等于检索正确率
- 模型看到的是预算受限、去重、截断后的挑选版上下文，不是完整历史真相

## 排障时先看什么

如果记忆行为异常，优先区分是哪一层：

1. 候选没有被识别
2. 候选识别了，但配置不允许自动写入
3. 文件写入成功了，但索引还没追平
4. 搜索命中了，但 recall / prompt 注入没有对上
5. 压缩任务已经入队，但后台 worker 还没跑或跑失败

很多表面上的“记忆差”问题，最后都不是模型问题，而是分类、落点、同步和预算边界没有对齐。

## 后台维护循环

当前实现中有两个独立的后台维护循环：

### 小时级维护（index.ts 每小时）

1. **全局 eviction**：清理低价值过期记忆（importance <= 2 && access_count = 0 && age > 30d），每小时执行一次。
2. **per-user LLM merge**：对超过阈值的用户，按分类调用 LLM 合并语义重复的记忆，并发射 MERGE 事件。

### 4 小时级固化（Soul Consolidation）

1. **观察提升**：高信号观察提升为持久记忆，发射 PROMOTE 事件并写入 source_event_id。
2. **洞察激活/退役**：低信心洞察退役，高信心洞察激活。
3. **亲和力合并**：基于 token Dice 系数（阈值 0.6）合并同分类内语义重叠的记忆，发射 MERGE 事件。
4. **观察修剪**：清理过期观察。

## PreThink 评估

在 recall 开始前，shouldSkipDurableRecall 会先判断查询是否值得发起昂贵的记忆检索：

- 查询长度 < PRETHINK_MIN_QUERY_LENGTH（默认 4，可通过 config 调整）时跳过
- 匹配问候/感谢等対话性短语时跳过

这避免了对“你好”“谢谢”等无语义查询浪费向量计算和搜索资源。
