# 安全模型

## 先说结论

NanoClaw 是本地高权限工作台，不是操作系统级沙箱产品。很多功能直接作用于文件系统、Git 仓库、浏览器、终端和本地运行目录。

## Web 侧保护

当前 Web 侧至少有这些保护层：

- 可选登录认证
- 受信 origin 校验
- 内部 API 授权
- 配置与高风险修改的审计入口

如果把服务直接暴露到不可信网络，这些保护并不足以把它变成公网多租户系统。

## 用户与权限（RBAC）

当前系统实现了基于角色的访问控制：

- `users`：用户注册与管理
- `roles`：角色定义
- `permissions`：权限定义
- `role_permissions`：角色-权限绑定
- `user_roles`：用户-角色绑定
- `auth_sessions`：认证会话

RBAC 模型控制 API 级别的访问权限，与 Web 登录认证联动。部分 route 模块（如 `auth-routes`、`user-routes`）直接依赖此机制。

## 访问策略

目录访问策略是第一层硬边界，当前模式包括：

- `allowall`
- `allowlist`
- `readonly`

它会影响 Agent 对本地目录的触达范围。

## 高风险能力

以下能力都应视为高风险：

- Web 终端
- 浏览器控制
- Repo Review hooks 安装
- 远端分支同步
- 扩展安装
- MCP / Skills 扩权
- 代码索引重建
- 知识库文档上传（会被分块并进入向量索引）

### 本机能力策略

Web 终端和浏览器控制属于本机高风险能力，由统一能力策略控制：

- 单用户模式：保留本地工作台行为，能力是否开放取决于对应 `WEB_*_ENABLED` 开关。
- 多用户模式：默认不可用；必须先由管理员显式启用全局开关，再授予细粒度权限。
- 终端使用 `terminal.access` 权限，浏览器控制使用 `browser.control` 权限。
- `browser_cli` 渲染抓取虽然不走浏览器控制 API，但同样按本机能力策略净化 runner 环境，未授权用户不会拿到可执行浏览器命令。
- MCP / Skill / 扩展的安装、导入、更新、删除等本机写操作使用 `local.install` 权限；该门禁不影响用户查看和使用自己已隔离的数据。
- Repo Review 的 hooks 安装/卸载、SSH key 管理，以及手动远端同步这类会修改本地 mirror / `.git/hooks` / 本机凭据的动作，也应走 `local.install`。
- 前端隐藏入口只是体验层；后端 HTTP route 和 WebSocket 握手仍是强制边界。

## 渠道安全

- 外部渠道依赖各自 token、secret 或 webhook
- sender trust 配置错误会带来误触发风险
- 外部消息并不天然可信

## 数据库安全

- 支持 SQLite / MySQL / PostgreSQL 三种引擎
- PostgreSQL 连接支持 SSL 配置（`DB_PG_SSL_REJECT_UNAUTHORIZED`、`DB_PG_SSL_CA_PATH`）
- 数据库凭据通过环境变量传递，不应硬编码

## 多用户数据隔离

当部署为多用户模式时，系统在以下维度实现租户隔离：

### 隔离模型

| 模块 | 隔离机制 | 可见性规则 |
|------|---------|-----------|
| 助手 | `assistants.user_id` + `visibility` | 自有 + 系统级 + shared |
| 知识库 | `knowledge_bases.user_id` + `visibility` + `user_knowledge_bindings` | 自有 + 系统级 + shared |
| AI 提供商 | `ai_providers.user_id` + `provider_user_access` | 自有 BYOK + 系统公开/受限 |
| MCP/Skills | `user_mcp_servers.user_id` / `user_skills.user_id` | 自有 + shared |
| 代码审查 | `review_repository_members` + `resource_access` | 成员 + 分享 |
| 对话 | `chats.user_id` + `conversation_ownership` | 自有 + 分享 |

### 提供商解析链

1. 请求/对话级 override
2. 用户默认提供商（`is_default = 1 AND user_id = ?`）
3. 系统默认提供商（`user_id = '__system__'`）
4. ENV / 硬编码 fallback

支持按功能模块配置不同提供商（`DEFAULT_PROVIDER_web_chat`、`DEFAULT_PROVIDER_code_review` 等），每级都遵循可见性检查。

### 磁盘隔离

- MCP/Skills 数据按用户目录隔离：`data/users/{userId}/mcp-servers/`、`data/users/{userId}/skills/`
- 启动时仅重建系统/共享数据，用户数据按需懒加载
- k8s 部署通过 PVC 持久化 + DB 启动重建兜底

## 最小安全基线

- 默认只在可信网络内使用
- 非必要不要开启 Web 终端
- 为高权限 Assistant 单独配置访问策略
- 不要直接安装来源不明的扩展或 Skills
- 对 Repo Review webhook 开启签名校验
- 配置 RBAC 角色和权限，控制敏感 API 的访问范围
- PostgreSQL 部署时启用 SSL 证书校验
