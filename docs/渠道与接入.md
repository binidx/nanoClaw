# 渠道与接入

## 当前内置渠道

- `web`
- `feishu`
- `telegram`
- `discord`
- `slack`
- `gmail`
- `whatsapp`

这些渠道共享同一套 conversation/runtime 基础设施，但每个渠道自己负责 JID 结构、group folder 派生、入站处理和平台侧发送。当前 Feishu、Telegram、Discord、Slack、Gmail 有适配器层入站去重；WhatsApp webhook 也会用平台 message id 做内存去重，并结合已持久化消息检查降低重复入站风险。WhatsApp 入站处理会等待元数据写入、自动注册和消息持久化完成后再返回 webhook ACK，避免平台已收到 200 但本地落库失败。

## 会话创建的两条路径

当前实现里，会话并不只来自手工配置后的显式创建。

第一条路径是主动创建：

- 通过 `POST /api/conversations` 创建新会话
- Web 控制台的统一“创建对话”弹窗会走这条路径

第二条路径是被动发现：

- 外部渠道收到首条入站消息后，可自动注册会话
- 会先落元数据，再决定是否进入后续消息处理链路

这意味着“有没有 conversation”不只取决于用户是否在 UI 上点过创建按钮。

## 渠道元数据驱动的创建入口

前端并不是写死渠道列表和字段，而是消费后端提供的 metadata：

- `channelTypes`
  描述渠道类型及其字段
- `conversationTargets`
  描述哪些渠道支持主动创建、是否依赖实例、需要哪些目标字段
- `channelInstances`
  描述当前启用的实例

因此当前创建对话弹窗是元数据驱动的，而不是一个静态表单。

当前实际生效的渠道实例配置来源是全局 `CHANNEL_INSTANCES` 配置和 `/api/channel-config`。仓库中还存在 `/api/user/channels` 与 `channel-connection-manager` 的用户级实例路径，但它尚未接入主 Settings 表单和主运行时 channel factory。

## 运行时路由与持久化元数据是两层数据

渠道接入时会同时维护两类状态：

- `registered_groups`
  运行时路由视图，保存 `jid`、folder、trigger、assistantId、`requiresTrigger`、agentConfig 等
- `chats`
  持久化会话元数据，保存 `name`、`custom_title`、`channel`、`is_group`、`last_message_time`

这样设计的原因是：

- 运行时路由需要服务消息消费和工作区定位
- 持久化元数据需要服务 UI 列表、搜索和展示

两者都重要，但职责不同。

## JID 与 group folder

`jid` 和 `group folder` 都是渠道特定派生值，通常还带实例维度。它们决定：

- 消息归属到哪个 conversation
- 运行时该使用哪个工作目录
- 重启恢复时如何找回已注册 group
- 不同实例下同一平台会话是否会互相冲突

因此这两者不是简单显示字段，而是运行时主键的一部分。

## `storeChatMetadata` 的作用

会话发现时，系统常常先调用 `storeChatMetadata` 维护 `chats` 表中的元数据，而不是立刻把所有正文都当作可执行输入持久化。

这样做的目标是：

- 先让控制台知道“有这个会话”
- 最小化无关正文的落库
- 为后续 sender trust、trigger、去重和路由判断提供基础信息

## 入站去重

外部渠道通常都要先做去重，再入库或入队。常见方式包括：

- 使用平台原生 message id
- 结合 `hasStoredMessage(...)` 这类数据库检查
- 针对 webhook/replay 做幂等保护

没有这层去重，很容易出现重复消费和重复回复。

WhatsApp 去重状态分两层：进程内 `seenIds` 只覆盖当前进程窗口，重启后依赖 `messages(chat_jid, id)` 的已持久化检查继续过滤平台重投；如果消息持久化失败，本次 webhook 不会把 message id 记录为已处理，平台重试仍可再次落库。

## transport metadata 与 UI title 分离

当前命名语义需要明确区分：

- `name`
  渠道发现的真实会话名或 transport metadata
- `custom_title`
  用户自定义标题
- `display_name`
  UI 展示时的派生结果

为什么不能混用：

- 渠道侧 metadata 刷新时可能会更新 `name`
- 用户标题必须稳定，不应被渠道同步覆盖
- 前端需要稳定的展示优先级，而不是每个页面各自猜测

## Web 渠道

Web 渠道是默认主入口，特点是：

- 会自动为 Web 对话派生 group folder
- 用户消息会被包装成带 `@AssistantName` 的入站文本，以复用同一套触发和路由逻辑
- 前端展示时再去掉这层包装

从助手入口发起创建时，当前约束也是只支持 Web 对话。

## 前端中的职责拆分

当前 UI 已把“接入配置”“接入运行态”“创建对话”拆开：

- `SettingsPage`
  负责渠道实例配置
- `ChannelsPage`
  负责运行状态与 Doctor 观测
- 创建对话弹窗
  负责消费 metadata 生成创建表单

这样设计的原因是实例配置、运行观测和会话创建属于三种不同频率和风险级别的操作。

## 外部渠道的共同前提

- 需要各自平台的 token、secret 或 webhook 配置
- 不同渠道的 sender 信息可信度不同
- 如果未配置对应凭据，前端只能显示能力入口，不能视为开箱即用
- WhatsApp 入站 webhook 需要实例 `verifyToken`；POST 签名校验需要实例 `appSecret` 或全局 `META_APP_SECRET`。签名校验使用 Meta 的 `x-hub-signature-256` 和原始请求 body，不能用重新序列化后的 JSON。字段 UI 可选不等于 webhook 可用。

## 风险提示

- 外部渠道接入一定伴随密钥和 webhook 管理
- Sender allowlist 与触发策略配置错误，会导致误触发或漏触发
- 外部渠道消息同样可能触发高权限本地行为
- 如果命名字段或 JID 设计理解错误，问题通常表现为“标题乱跳”或“会话被路由到错误工作区”
