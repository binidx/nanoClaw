# 代码智能图谱优化文档

## 1. 背景与目标

NanoClaw 之前已经有 `CodeMap`、`CodeIndex`、`CodeLLM` 三条能力线，但它们更像并列功能，而不是一套统一的“项目理解底座”：

- `CodeMap` 更偏文件树和结构快照，适合浏览，不适合深度问答。
- `CodeIndex` 已经有 chunk、文件摘要、函数与调用边，但过去没有成为所有上层能力的统一入口。
- `CodeLLM` 的效果强依赖 prompt 里喂进去的上下文质量，过去容易出现“看起来懂项目，实际上上下文不够精准”的问题。

这会导致三个直接问题：

- 项目问答很难稳定回答“这个功能在哪里实现”“改这里会影响哪里”。
- Repo Review、CodeMap AI 分析、后续工作流助手各自重复做一遍上下文拼装，效果不一致。
- Agent 很容易读取过多文件，既慢又贵，还会把注意力浪费在无关代码上。

本次优化的目标不是继续堆功能，而是把代码理解能力收敛成一套可复用的图谱式检索底座，服务于：

- 项目实现问答
- CodeMap AI 总结与仓库描述
- Repo Review / AI Code Review
- 后续工作流里的“按需读代码”“只关注必要上下文”

如果只看目标表达，这套设计接近 graphify 的核心价值：把仓库先变成结构化图谱，再用图谱做最小上下文检索，而不是每次临时拼 prompt。

## 2. 对旧方案的判断

### 2.1 CodeMap 是否有用

有用，但定位需要下调。

`CodeMap` 适合作为：

- 仓库结构总览
- 目录/文件导航层
- 面向人的可视化入口

`CodeMap` 不适合作为：

- 唯一的项目理解引擎
- 项目问答的主检索层
- Repo Review 的主要证据来源

原因很简单：它天然偏“树”，不偏“关系”。它知道文件在哪里，但不天然知道函数怎样跨文件连接、某个能力通过哪些调用链落地、某个目录的真实职责边界是什么。

### 2.2 CodeIndex 是否有用

非常有用，而且应该成为主底座。

`CodeIndex` 已经具备几个关键资产：

- 文件级摘要
- chunk 级摘要与代码片段
- 函数定义
- 函数调用边
- 分支级 snapshot 与持久化

这些数据一旦统一成图结构，就能支撑比 `CodeMap` 更强的问答、追踪和最小上下文检索。

### 2.3 CodeLLM 是否有用

有用，但它本质上不是底座，而是“消费底座的推理层”。

如果 `CodeLLM` 只能拿到粗糙文件树或少量关键字匹配结果，它会表现得很像“会说，但不够准”；如果它拿到的是文件摘要、chunk 摘要、函数邻域、跨文件热点和最短路径，它的效果会明显提升。

所以核心结论是：

- `CodeMap` 保留，但转为结构展示层。
- `CodeIndex` 升级为主代码智能底座。
- `CodeLLM` 只在统一检索层之上工作，不再自己承担“理解整个项目”的责任。

## 3. 参考 graphify 的设计原则

graphify 最值得借鉴的，不是“把代码画成图”这件事本身，而是下面几条原则：

- 单一图谱底座：不同上层能力共享同一份结构化理解结果。
- 多粒度节点：目录、文件、代码块、函数不是平级替代，而是可联通的多层节点。
- 显式关系边：`contains`、`imports`、`calls`、`references` 比单纯文本搜索更适合回答“实现在哪里”和“影响路径是什么”。
- 最小上下文检索：先找最相关的起点，再扩展 1-hop / 2-hop 邻域，而不是直接把整堆文件塞给模型。
- 可解释性：为什么命中这个文件、这段代码、这条路径，最好都能回溯。
- 可复用性：问答、审查、工作流、规划应该共享一套图谱，而不是各写一套检索逻辑。

本次优化基本沿着这条线做，但目前仍然是“graph-aware retrieval 初版”，还不是 graphify 完整形态。

## 4. 本次优化后的总体架构

当前更合理的分层是：

1. `CodeMap`
   负责结构快照、文本渲染、目录级展示和人类浏览入口。
2. `CodeIndex`
   负责分支级 snapshot、chunk、文件摘要、函数、函数调用边、持久化。
3. `ProjectGraph`
   负责把 `CodeIndex + CodeMap` 统一成可查询的项目图谱。
4. `CodeLLM / Repo Review / 工作流助手`
   负责消费 `ProjectGraph` 输出的最小上下文结果。

对应代码入口：

- 构建与持久化：`src/code-intelligence/code-index-builder.ts`
- CodeMap / AI 分析：`src/routes/code-map-routes.ts`
- 项目图谱与检索：`src/code-intelligence/project-graph.ts`
- 图谱问答与关系 API：`src/routes/code-index-routes.ts`
- Repo Review 证据编排：`src/repo-review/repo-review-run-executor.ts`

## 5. 已落地的核心优化

### 5.1 统一构建与持久化

过去 `CodeMap` 和 `CodeIndex` 有明显并行感，现在开始统一到 `CodeIndex` 这条主链上：

- `CodeMap` 重建前端入口会触发统一的 `CodeIndex` 重建。
- `CodeIndex` 的分支 snapshot、基础内容、摘要进度、向量增强状态都持久化落库。
- 首次 snapshot 可先可用，摘要/向量增强后补，降低“必须全部跑完才可用”的延迟。

这一步的意义是把“项目理解的真实资产”从一堆临时缓存，变成可复用、可恢复、可被多个能力共享的稳定数据层。

### 5.2 CodeMap AI 分析开始消费 CodeIndex

`CodeMap` 的 AI summary / repo description 不再只盯着目录结构，而会吸收：

- 文件摘要
- chunk 摘要
- 代表性代码片段
- 函数图邻域

这让 CodeMap 的 AI 输出从“结构介绍”提升到了“结构 + 关键实现 + 模块关系”的混合描述。

### 5.3 Repo Review 的图谱证据增强

Repo Review 当前已经不只是看 diff，而是把下面这些证据拼到 evidence bundle 里：

- 变更文件摘要
- 相关函数定位
- 1-hop 函数调用邻域
- 文件级影响
- 函数级影响

这说明代码图谱已经开始从“展示型能力”进入“生产型能力”。

### 5.4 新增 Project Graph 检索层

这次最关键的新能力是 `src/code-intelligence/project-graph.ts`。

它把 `CodeIndex + CodeMap` 收敛成一张缓存图，当前节点与边模型如下：

- 节点类型：`directory`、`file`、`chunk`、`function`
- 关系类型：`contains`、`imports`、`calls`、`references`
- 边置信度：`EXTRACTED`、`INFERRED`、`AMBIGUOUS`

当前还支持：

- 节点解释：为什么这个节点重要、它连向哪里、被谁引用
- 路径搜索：两个实现点之间的最短路径
- BFS / DFS 图检索：围绕问题扩展最小邻域
- fallback answer：即使暂时不走模型，也能先给出结构化回答草稿

## 6. 项目图谱检索层设计

### 6.1 为什么它比旧 CodeMap 强

旧 `CodeMap` 更容易回答：

- 仓库里有哪些目录
- 某个目录下面有什么文件

新的 `ProjectGraph` 更容易回答：

- 某个功能在哪里实现
- 某个接口最终落在哪些函数上
- 改某个函数时，可能波及哪些文件和邻近调用点
- 两个模块之间是否真实存在实现路径

这是从“结构浏览”走向“实现追踪”的本质变化。

### 6.2 为什么它能减少上下文

旧做法经常是“先搜一堆文件，再丢给模型判断”。问题是：

- 命中面太宽
- 低相关文件很多
- 模型注意力会分散

`ProjectGraph` 的思路是：

1. 先做节点匹配，找到问题最可能涉及的起点。
2. 再按 BFS / DFS 和关系过滤扩展局部邻域。
3. 最后只输出局部子图、相关 chunk、函数和少量摘要给上层模型。

这样做有三个直接收益：

- 上下文更小
- 命中更准
- 模型更容易围绕“实现链条”而不是“文件列表”回答

### 6.3 当前 API 面

已经新增的图谱能力入口如下：

- `GET /api/code-index/:repositoryId/graph/stats`
- `POST /api/code-index/:repositoryId/graph/query`
- `GET /api/code-index/:repositoryId/graph/path`
- `GET /api/code-index/:repositoryId/graph/explain`
- `POST /api/code-index/:repositoryId/ask`

这五个入口已经足够支撑：

- 项目问答
- 关系追踪
- 命中理由解释
- 上层 Agent 的最小上下文检索

## 7. 对项目问答的实际意义

如果目标是问：

- “这个功能在哪里实现的？”
- “某个按钮点击后会走到哪里？”
- “这个模块和 Repo Review 的哪部分有关？”

那么当前这套优化已经比旧版强很多，因为它至少具备了：

- 文件级语义摘要
- chunk 级代表性实现片段
- 函数级定义与调用边
- 目录到函数的多跳可达关系
- 最短路径与节点解释

这意味着它已经不是简单的 code search，而是开始具备“项目实现问答”的骨架。

更重要的是，这套骨架是可复用的。后续无论是 AI CR、工作流编排、开发助手还是仓库问答，都不应该再各自单独做上下文拼装，而应统一消费 `ProjectGraph` 的子图结果。

## 8. 当前效果与 graphify 的差距

结论很明确：现在已经明显比原来的 `CodeMap + CodeLLM` 强，但还没有完全追平 graphify。

当前已经接近的部分：

- 多粒度节点
- 显式关系边
- 图查询入口
- 最小上下文检索思路
- 面向问答和审查的复用方向

当前仍有明显差距的部分：

- 当前 community 已有轻量图结构标签传播聚类，并用公共目录生成 label；它仍不是完整 graphify 级社区发现。
- 已落地 query / ask artifact 持久化；仍未导出完整 `graph.json`、HTML 浏览页、community-report 等图谱产品层产物。
- 还没有更丰富的节点类型，例如 class、type、interface、route、test、schema、table、workflow node。
- 还没有更强的跨层关系，例如“HTTP route -> service -> db -> review flow -> workflow step”。
- 还没有完善的命中置信度与证据评分体系。
- Repo Review 已接入统一 `ProjectGraph` prepared context，但主审查仍混合使用 evidence bundle、CodeMap / CodeIndex 和手工 impact graph。
- 还没有形成一个通用的“项目问答执行器”，目前 `/ask` 还是基于当前图谱结果生成回答上下文，而不是完整的图谱型 agent loop。

所以更准确的判断是：

- 在 NanoClaw 当前代码库内，这已经是从“结构辅助”走向“图谱检索底座”的关键跃迁。
- 但如果以 graphify 作为满配目标，现在仍处于“图谱检索层已落地、图谱产品层与图谱推理层仍需继续增强”的阶段。

## 9. 为什么这套设计对 AI CR 和工作流复用很重要

如果不做统一图谱层，AI CR、项目问答、开发工作流会反复踩同一个坑：每个能力都要自己决定读哪些文件、怎么缩上下文、怎么解释影响范围。

统一图谱层的价值在于：

- 问答用它找“最相关实现链”
- Repo Review 用它找“变更影响与邻域证据”
- 工作流助手用它做“只读必要文件”
- 后续多 Agent 协作可以先基于图谱切分模块，再分配子任务

这实际上会同时提升三个指标：

- 质量：减少答非所问和漏看关键实现
- 成本：减少无关上下文
- 速度：减少 Agent 的盲目探索

## 10. 最佳效果导向的后续路线

如果不考虑开发成本，只追求效果，后续最值得投入的不是再补几个零散 API，而是把 `ProjectGraph` 从“项目问答辅助层”推进成“全局代码理解执行层”。

### 10.1 目标终态

理想状态下，NanoClaw 里的所有“读项目代码再思考”的能力，都应该先经过同一条路径：

1. 读取分支级 `CodeIndex` / `CodeMap` / graph artifact
2. 进入统一的 query planner
3. 由 planner 选择检索策略、关系过滤器、深度和上下文预算
4. 返回最小子图、命中证据、路径解释和上下文片段
5. 上层能力再决定是直接回答、继续补证，还是发起受控工具调用

在这个终态里：

- Repo Review 不再自己拼主要上下文，而是消费 graph retrieval 结果
- Workflow / Workteam 节点不再盲读仓库，而是先取问题相关局部子图
- 项目问答、AI CR、开发助手都复用同一套 path ranking、context filter、confidence 规则
- Agent 的“探索仓库”变成少量受控补证，而不是默认全仓搜索

### 10.2 主线一：把 Repo Review 直接接到 graph retrieval

这是下一步最值钱的优化。

现在 Repo Review 虽然已经消费了图谱增强过的 evidence bundle，但主审查链路仍然主要围绕 bundle 组织上下文。最佳效果方案应该改成：

1. diff -> graph seed extraction
   从变更文件、变更函数、import 变化、调用边变化里提取种子节点。
2. graph impact expansion
   基于 `calls`、`references`、`imports`、`contains` 做 1-hop / 2-hop 扩展，形成“变更影响子图”。
3. review query planning
   按变更类型决定检索模式：
   - 纯局部重构：偏函数邻域
   - API 入口修改：偏 route -> service -> persistence 路径
   - 配置 / prompt / workflow 修改：偏跨层引用和使用点
4. context filter
   对子图执行预算裁剪，只保留最有解释力的节点、边、chunk 和邻近测试。
5. reviewer execution
   主审查代理直接消费“图检索结果 + diff + 局部原文补证入口”，而不是先吃一个静态 evidence bundle。

这样改的核心收益：

- 审查上下文会从“静态包”变成“按问题扩展的局部图”
- 更容易回答“这个改动真正影响了哪里”
- 可以自然引入 path ranking、风险热点、桥接节点、邻近测试文件

最佳实践上，evidence bundle 不应该立即删除，而应该退化成 graph retrieval 的序列化产物：

- bundle 继续保留，用于持久化、回放、审计和 worker 输入
- 但 bundle 的来源改成统一 query pipeline，而不是专门在 Repo Review 内部单独拼装

### 10.3 主线二：把 Workflow / Workteam 节点直接接到 graph retrieval

这是第二条必须尽快推进的主线。

当前 Workflow 节点执行时，Agent 仍然很容易拿到一个宽泛任务后自行探索仓库。最佳效果方案应该是：

1. 每个 workflow node 在执行前先声明任务意图
   例如：实现功能、修 bug、写测试、做 code review、做架构分析。
2. runtime 根据任务意图生成 graph query
   例如：
   - 实现功能：找入口点、依赖函数、相关配置、相邻测试
   - 修 bug：找报错点、调用链、最后落库路径、相关 guard
   - 写测试：找被测函数、依赖 mock 点、相邻现有测试
3. workflow agent 先消费局部子图，再决定是否继续读文件
4. 若需要子代理拆分，则按 community / subgraph 边界拆，而不是按目录粗切

这一步会显著提升 Workflow 的复用价值，因为同一套图谱能力可以同时服务：

- 需求实现
- Bug 修复
- 测试补全
- 代码审查
- 技术调研

最重要的是，这会把 Workflow 从“带图形界面的通用 Agent 调度器”，推进成“有项目理解前置层的开发执行器”。

### 10.4 第一阶段：把图补全到“真正可问答”

要把上面两条主线做好，先要把图谱本身补全。

- 扩展节点类型：`class`、`interface`、`type`、`route`、`test`、`schema`、`table`、`config`、`prompt`、`workflow`
- 扩展边类型：`implements`、`extends`、`handles`、`persists_to`、`tested_by`、`configured_by`、`emits`、`subscribes`
- 加强符号解析，补更多跨文件 `references`
- 对动态调用、字符串注册、路由注册、barrel export 建立更稳的推断规则
- 为 route、db、workflow 节点建立跨层连接，让“入口到落库”可以形成真实路径

这一步完成后，项目问答和图驱动审查才会更稳定地回答“功能在哪里实现”“为什么影响这里”“有没有相邻测试”。

### 10.5 第二阶段：做真正的 community / hotspot / god node

这是追平 graphify 的关键差距之一。

- 基于图结构做社区发现，而不是只按目录前缀聚合
- 输出模块社区、跨社区桥接节点、god node、热点函数
- 为每个 community 建立摘要、入口点、核心文件、外部依赖面
- 结合 git blame / commit 热度 / review 历史，识别高风险区域

这一步的直接价值不只是“图更好看”，而是：

- Repo Review 可以优先关注跨社区变更
- Workflow 可以按社区切任务
- 项目问答可以先锁定相关 community，再做局部检索

### 10.6 第三阶段：做 confidence、path ranking、context filter

这是让图真正可用于生产推理的核心层。

#### 置信度分层

- 节点置信度：这个节点本身的来源是否可靠
- 边置信度：`EXTRACTED`、`INFERRED`、`AMBIGUOUS` 继续细化
- 路径置信度：一条路径是否由高可信边串联而成
- 回答置信度：当前回答主要建立在多少真实定义、多少推断关系之上

#### path ranking

- 更短路径优先，但不能只按 hop 数
- 高置信度边优先
- 穿过核心入口点、桥接节点、真实调用边的路径优先
- 低信息量目录边、弱引用边权重下调

#### context filter

- 按问题类型设置不同预算模板
- 保留高信息密度 chunk，丢弃解释力弱的文件
- 优先保留“定义 + 调用 + 使用点 + 测试”闭环
- 支持审查模式、实现模式、问答模式、测试模式的不同裁剪规则

这一步做完以后，`ProjectGraph` 才能真正成为“最小上下文调度器”。

### 10.7 第四阶段：做统一 query planner 与持久化图查询接口

现在有 query API，但还没有真正的统一执行层。下一步应该把它推进成稳定服务。

建议新增一层统一查询抽象：

- `locateImplementation`
- `traceCallPath`
- `estimateImpactScope`
- `findRelatedTests`
- `explainModuleResponsibility`
- `prepareReviewContext`
- `prepareWorkflowNodeContext`

这些接口都不直接暴露底层 BFS / DFS，而是暴露任务语义。

同时要继续补齐图谱产品层产物：

- query / ask artifact 已保存 query input、命中节点、命中路径、裁剪结果等基础轨迹
- 支持 query replay，便于审计“为什么这次审查读了这些文件”
- 仍需导出 `graph.json`、`community-report.json`、`query-trace.json`
- 提供 HTML 图谱浏览与 query 调试页

这是从“库函数”走向“平台能力”的分水岭。

### 10.8 第五阶段：把所有上层能力统一接到图谱层

当图谱和 query planner 足够成熟以后，上层能力应该全面收口：

- CodeMap AI summary 全量使用图谱检索结果
- Repo Review 的主审查、worker 审查、补证逻辑都改用统一 graph retrieval
- Workflow / Workteam 在读代码前先取局部子图
- 项目问答 `/ask` 升级成 planner 驱动，而不是当前直接 query + fallback
- 子代理任务切分基于 community 或边界子图，而不是简单按目录切

这一阶段的目标不是再新增能力，而是“消灭各条链路各自拼上下文的重复实现”。

### 10.9 第六阶段：做 graphify 级产品化输出

- 导出 `graph.json`
- 导出 HTML 图谱浏览页
- 生成聚类报告、入口点报告、风险报告
- 保存 query audit trail，支持回放“为什么给出这个答案”
- 输出项目级“理解摘要”，让新 Agent 进入仓库时先吃社区摘要而不是盲搜代码

这一步做完后，NanoClaw 才算真正拥有一套接近 graphify 的项目理解基础设施。

### 10.10 推荐实施顺序

如果按投入产出比排序，我建议实际推进顺序是：

1. `Repo Review -> graph retrieval`
   因为这是最直接提升 AI CR 质量的路径。
2. `Workflow / Workteam -> graph retrieval`
   因为这会让图谱能力开始在开发执行链里复用。
3. `community + path ranking + context filter`
   因为这是把图从“能查”变成“会筛”的关键。
4. `persistent query artifacts + planner`
   因为这决定了后续是否可审计、可调优、可平台化。
5. `graphify 级可视化与报告`
   因为它对理解和调试很有价值，但优先级低于真正影响 AI 决策质量的部分。

### 10.11 每阶段的完成标准

为了避免这套方案再次退化成“加功能点”，每一阶段都应该以效果验收：

#### Repo Review 接入完成标准

- 主审查默认上下文来自 graph retrieval，而不是手工 evidence 拼装
- 审查结果可展示“影响子图”和关键路径
- 审查读取文件数量下降，但有效发现率不下降

#### Workflow 接入完成标准

- workflow node 执行前自动获得局部子图
- 子代理拆分能按 subgraph/community 切分
- 同类任务的仓库探索步数明显下降

#### community / ranking / filter 完成标准

- 同一问题多次查询的命中更稳定
- 高置信路径明显优于单纯关键词命中
- 上下文 token 消耗下降，但回答解释性增强

#### 持久化 query 平台完成标准

- 任意一次项目问答、审查、workflow 执行都能回放 query trace
- 可以直接比较不同 planner / filter 策略的效果
- 图谱产物能脱离运行时单独导出和调试

## 11. 当前结论

这次优化不是简单重构，而是完成了一个关键方向调整：

- `CodeMap` 从主智能层退回展示层
- `CodeIndex` 升级为主数据底座
- `ProjectGraph` 成为统一检索层
- `CodeLLM`、Repo Review、未来工作流开始共享同一套项目理解能力

从结果上看，它已经明显优于旧版 `CodeMap + CodeLLM` 方案，也已经具备了“项目问答底座”的雏形；但如果目标是完全追平 graphify，目前仍有差距，差距主要不在代码结构，而在图谱完备度、社区发现、证据审计和统一问答执行器这几层。

换句话说：

- 这次优化已经把方向走对了。
- 现在最需要的不是重新设计，而是沿着 `ProjectGraph` 继续做深做满，把它从“图感知检索层”推进成“图谱级项目理解平台”。
