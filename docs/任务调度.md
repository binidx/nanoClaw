# 任务调度

## 支持的调度类型

- `once`
- `interval`
- `cron`

## 任务与会话的关系

任务不是独立于聊天系统之外的第二套执行器。当前任务模型总是绑定某个 conversation / group 上下文执行，复用同一套：

- Assistant 选择
- Access Policy
- 工作区目录
- Agent runtime
- 消息与结果持久化

这就是为什么任务页和聊天页天然联动。

## 前端的两层状态

任务页当前拆成：

- `TasksPageContainer`
  负责远程 truth，包括任务列表、加载、选中会话和轮询
- `TasksPage`
  负责筛选、排序、通知、编辑器、AI 草稿和 run monitor

这样设计的原因是任务页内部交互状态很多，但不值得都提升到 `App.tsx`；同时它又必须和当前激活会话保持同步。

## 选中会话与聊天页联动

当前前端会保留已有 `selectedChatJid`，再尝试跟随 `activeJid`。没有实现“无激活会话时自动回退到会话列表第一项”的强语义。因此任务页是 conversation-centric 的调度界面，但 selected chat 主要影响创建目标和表单默认值。

## AI 草稿链路

任务草稿并不是只做文本补全。当前典型流程是：

1. 在任务页选择当前会话
2. 输入自然语言描述
3. 后端把描述解析成结构化草稿
4. 根据结果决定直接创建，或进入高级表单微调

这让 AI 草稿更接近“调度意图解析”，而不是简单生成一段 prompt。

## 调度执行模型

当前执行链路大体如下：

1. 调度器扫描 due tasks
2. 对任务做 claim，避免重复并发执行
3. 通过 `GroupQueue` 把任务排入对应 conversation 的串行队列
4. 复用现有 Agent runtime 执行 prompt
5. 写回任务结果、错误、下一次执行时间和运行日志

这样设计可以保证：

- 同一 conversation 下，任务和普通消息不会无序抢占
- 任务执行结果天然带有会话上下文
- 失败恢复语义和普通对话更接近

## 为什么 `interval` 要锚定计划时间

当前 `interval` 不是“上一次跑完再加固定时长”，而是尽量锚定到原计划时间并跳过已经错过的窗口。这样做的原因是避免长期漂移，否则执行时长稍大就会把整个计划慢慢拖偏。

## 失败、重试与暂停

任务失败后不会简单地一直马上重试。当前策略包括：

- `retry_limit`
- `retry_backoff_ms`
- 指数退避
- `failure_mode`
  例如继续下一个常规执行，或直接暂停

这套设计是为了防止异常任务在本地环境里持续抖动，占满队列或反复触发高权限动作。

## 当前轮询语义

后端 `/api/tasks` 支持 `chat_jid` filter，但当前前端 `TasksPageContainer` 实际加载和轮询的是全量 `/api/tasks`。如果要恢复 conversation-scoped 局部轮询，需要前端显式接入 `chat_jid` query。

这样做的原因是：

- 当前实现更简单，避免多个局部 truth，但大规模任务运行时会产生全量列表刷新成本。

## 当前能力

- AI 生成任务草稿
- 创建与编辑任务
- 手动立即执行
- 暂停与恢复
- 删除任务
- 运行态查看
- 结果与快照持久化

## 适合的场景

- 定时摘要
- 周期性巡检
- 固定格式的自动分析
- 面向某个群组上下文的重复性任务

## 注意事项

- 高权限任务会继承对应会话的目录和运行时能力
- 调度错误往往不是前端问题，而是 Provider、上下文或本地环境问题
- 任务过大时，应拆成更小的独立任务，避免单次运行过重
- 如果任务看起来“没执行”，先区分是没进入 due、没成功 claim、没排进队列，还是运行后失败
