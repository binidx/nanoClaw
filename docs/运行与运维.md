# 运行与运维

## 安装准备

推荐顺序：

```bash
npm install
cd web && npm install
cd ../agent/runner && npm install && npm run build
cd ..
npm run build
npm run onboard
```

这一步的真实目的是同时满足三类运行前提：

- 后端 TypeScript 构建产物存在
- 前端静态资源可被托管
- `agent/runner/` 已具备可执行 runtime

只完成其中一部分，通常不足以把整个系统跑起来。

## 启动

macOS / Linux：

```bash
./start.sh
```

Windows：

```bat
start.bat
```

脚本层会做依赖检查和构建，真正进入 `src/index.ts` 后的启动流程大致是：

1. 初始化数据库与 schema（根据配置选择 SQLite / MySQL / PostgreSQL 引擎）
2. 等待 `loadState()` 恢复 `router_state`、`sessions`、`registered_groups`
3. 恢复 pending messages，避免重启后重复或漏消费
4. 恢复孤儿 subagent runtime
5. 连接渠道
6. 启动 scheduler、context compaction、trash cleanup、IM AI、memory maintenance、soul consolidation、knowledge maintenance、IPC watcher、repo review auto sync / digest loop
7. 启动 Web server 与 WebSocket
8. Web server 成功监听后写入 `nanoclaw.pid` / `nanoclaw.port`
9. 启动主消息循环

启动恢复不是单一事务：`loadState()`、pending message recovery、渠道连接和后台循环存在短暂并行窗口。排查重启后重复消费或漏消费时，要同时查看 `router_state`、`sessions`、`registered_groups`、`messages` 和对应渠道的去重语义；例如 WhatsApp 会在重启后用已持久化消息检查补足进程内去重状态。

## 停止

macOS / Linux：

```bash
./stop.sh
```

Windows：

```bat
stop.bat
```

停止脚本会优先读取 PID/端口信息定位旧进程。运行时自身还会在收到 `SIGTERM` / `SIGINT` 时：

- 关闭 `GroupQueue`
- 断开所有渠道
- 退出进程

## 运行时标记文件

- `nanoclaw.pid`
- `nanoclaw.port`

这两个文件由 `src/index.ts` 直接写入。它们适合用于：

- 判断当前是否已有 NanoClaw 运行
- 定位 Web 控制台端口
- 停止脚本按 PID 优先清理旧实例

## 后台常驻循环

当前系统不是"仅 Web 请求驱动"的服务，启动后会有多条常驻循环同时工作：

- 主消息轮询循环
- 任务调度循环
- context compaction loop
- memory maintenance / knowledge maintenance loop
- IPC watcher
- Repo Review auto sync loop

运维上看到 CPU、IO 或日志持续活动时，通常先判断是哪条循环在工作，而不是先假设是异常。

## Web 控制面可观测入口

最有价值的几个接口：

- `/api/status`
  看 channels、active agents、queued tasks、subagents、memory 概况
- `/api/doctor`
  看环境、provider、配置和关键依赖诊断
- `/api/conversations`
  看会话列表是否正常聚合

如果 Web UI 正常但聊天行为异常，`/api/status` 往往比页面本身更先暴露问题。

## 常用运维命令

```bash
npm run doctor
npm run onboard -- --check --json
npm run build:all
```

常见使用方式：

- 首次部署前先跑 `npm run onboard`
- 配置或环境怀疑有问题时跑 `npm run doctor`
- 怀疑构建产物不同步时跑 `npm run build:all`

## 数据库引擎选择

当前支持三种数据库引擎：

- **SQLite**（默认）：零配置，适合单机部署和开发环境
- **MySQL / TiDB**：适合需要外部数据库的部署场景
- **PostgreSQL**：适合需要高级查询和并发能力的部署场景

引擎选择通过环境变量配置，`src/database/factory.ts` 根据配置创建对应引擎实例。

迁移脚本：`scripts/migrate-to-postgres.ts` 可将 SQLite / MySQL 数据迁移到 PostgreSQL。

## PostgreSQL SSL 配置

当使用 PostgreSQL 作为数据库后端时，以下环境变量控制 SSL 连接行为：

- `DB_PG_SSL_REJECT_UNAUTHORIZED`
  是否校验服务端证书。默认 `true`。设为 `false` 可跳过证书校验（仅建议内网或测试环境使用）。
- `DB_PG_SSL_CA`
  自定义 CA 证书内容或路径配置。当前实现读取该变量来构造 PostgreSQL SSL CA 选项。

这些配置通过 `src/database/postgres-engine.ts` 的连接池初始化生效。

## 典型运行期风险点

### `ALLOW_INSECURE_TLS`

若配置启用，运行时会直接设置：

```text
NODE_TLS_REJECT_UNAUTHORIZED=0
```

效果是关闭上游 HTTPS 证书校验。它适合临时排查内网证书问题，但不应当作常态配置。

### Web 端口冲突

`createWebServer(...).start()` 在启动监听阶段遇到 `EADDRINUSE` 会 reject，顶层 `main()` 捕获后退出进程。监听成功后的 server error 才主要表现为日志告警。排障时应先确认端口是否被占用，再判断是否进入了后续消息循环。

### 孤儿 subagent runtime

启动期会扫描并恢复 orphaned subagent runtime。若日志里出现恢复告警，说明上次退出可能不是干净关停。

## 服务化

仓库里的 `setup/` 支持服务化辅助逻辑：

- macOS：`launchd`
- Linux：`systemd`，无 systemd 时可退回 `nohup`
- Windows：Task Scheduler

服务化部署时，应额外确认：

- 工作目录固定
- `groups/`、`data/`、`store/` 有稳定写权限
- Provider 凭据与渠道凭据能被服务进程读取
- 数据库连接配置（如 MySQL / PostgreSQL）在服务环境下可达

## 最小巡检项

- `nanoclaw.port` 指向的端口是否可访问
- `/api/status` 与 `/api/doctor` 是否返回正常
- 默认 Provider 是否可连通
- 关键渠道是否连接成功
- 是否存在大量 queued task 或 active agent 长时间不释放
- 任务、Repo Review、浏览器、终端等高风险模块是否只在需要时开启
- 数据库连接是否稳定（MySQL / PostgreSQL 部署时）

## 容易误解的点

- `setup.sh` / `setup.ps1` 不是完整首启入口
- 本项目默认是本机工作台，不是无状态服务
- 只构建后端并不代表前端和 agent runner 已经可用
- Web UI 失效不一定等于后台消息循环停止
- 运维时不要只盯 `messages` 表；很多恢复语义还依赖 `router_state`、`sessions` 和 `registered_groups`
- `src/database/` 是引擎抽象层，`src/db/` 是业务 CRUD 层，两者不应混淆
