# 系统概览

## 产品定位

NanoClaw 是一个本地优先的 AI 工作台。它把聊天、自动化任务、代码审查、股票分析、知识库、灵魂与记忆、用户权限、浏览器操作、渠道接入与运行时扩展放在同一套控制台里，但底层不是"页面功能的简单拼盘"，而是一套围绕本地目录、会话工作区、多数据库持久化（SQLite / MySQL / PostgreSQL）和本地 Agent 子进程组织起来的运行时。

## 运行形态

- 单个 Node.js 进程同时承载 HTTP API、WebSocket、静态资源托管和后台循环
- Web 前端位于 `web/src`
- Agent 通过本地子进程执行，后端通过 `src/agent/agent-runner.ts` 及 `src/agent/*` 子模块作为桥接层
- 事实状态主要落在数据库（默认 SQLite `store/messages.db`，可切换 MySQL / PostgreSQL）
- 热状态保留在进程内，并通过少量持久化游标在重启时恢复
- 会话级工作区位于 `groups/`，上传、扩展、MCP 等运行时数据位于 `data/`
- 多用户模式下，助手、知识库、仓库、MCP/Skills、Provider 与会话均通过 `user_id` / 显式授权 / visibility 组合隔离；普通用户不会自动继承 `__system__` private 资源。AI Provider 区分自有、分享给我的、系统三类来源：个人 Provider 默认私有，所有者可按用户分享；系统 Provider 可设 public 全局默认，也可用 restricted 绑定用户或角色。

### 2. 热状态

只在当前进程内有效，但会按需写回 `router_state` / `sessions`：

- `registeredGroups`
  当前活跃会话到运行时 group 的映射
- `sessions`
  当前会话对应的 Agent 会话 ID
- `lastTimestamp`
  全局消息轮询水位
- `lastAgentTimestamp`
  每个会话已提交的消费游标
- `pendingAgentTimestamp`
  每个会话"已取到但尚未确认输出"的 pending 游标
- `pendingUploadedFiles`
  尚未和持久化消息对齐的上传文件上下文

设计上把事实状态和热状态拆开，是为了同时满足两件事：

1. 数据库仍然保留可恢复、可查询、可回放的事实。
2. 消息编排和流式输出不必把每一步都做成重事务。

## 会话一致性模型

会话一致性不只靠 `messages` 表，核心还依赖 `src/index.ts` 的游标协议：

- `lastAgentTimestamp`
  已提交游标。表示该时间点之前的用户消息已经被系统稳定消费。
- `pendingAgentTimestamp`
  待提交游标。表示消息已经取出并进入 Agent 处理，但是否真正对用户可见还未确认。

标准流程：

1. 消息循环通过 `getNewMessages(...)` 拉到新消息，并先推进全局 `lastTimestamp`。
2. 针对每个会话，`processGroupMessages(...)` 再通过 `getMessagesSince(...)` 取该会话自上次 committed cursor 以来的增量。
3. 在真正运行 Agent 前，先把最后一条待处理消息的时间戳写进 `pendingAgentTimestamp`。
4. Agent 输出过程中，turn 事件和最终消息分层持久化并广播。
5. 只有在输出被确认可见后，pending cursor 才会提交到 `lastAgentTimestamp`。
6. 如果运行失败且没有用户可见输出，pending cursor 会被清掉，消息允许重试。

这样设计的原因是：

- 单看"Agent 子进程是否返回成功"不足以判断用户是否真正看到了结果。
- 只有把"消息已取出"和"结果已稳定落地"分开，才能避免重启后重复消费或误跳过消息。

## 启动生命周期

从 `src/index.ts` 的 `main()` 看（实际逻辑分布在 `runtime-state.ts`、`runtime-dispatch.ts`、`runtime-channels.ts`、`runtime-persistence.ts`），启动顺序大致是：

1. `initDatabase()` 初始化数据库和 schema（根据配置选择 SQLite / MySQL / PostgreSQL 引擎）
2. 读取配置，必要时打开 `ALLOW_INSECURE_TLS`
3. 等待 `loadState()` 恢复 `router_state`、`sessions`、`registered_groups`
4. 恢复 pending messages，避免重启后重复或漏消费
5. 恢复孤儿 subagent runtime
6. 连接各个已启用渠道
7. 启动 Repo Review auto sync 与 digest loop
8. 启动 scheduler、context compaction、trash cleanup、IM AI、memory maintenance、soul consolidation、knowledge maintenance、IPC watcher 等后台循环
9. 创建并启动 Web server
10. Web server 成功监听后写入 `nanoclaw.pid` / `nanoclaw.port`
10. `recoverPendingMessages()` 把未处理消息重新入队
11. 启动主消息循环 `startMessageLoop()`

需要注意：当前 `loadState()` 在 `main()` 中是 fire-and-forget，内部 pending cursor timestamp reconcile 也不是启动主链路的强同步前置条件。因此运行时恢复、渠道连接、Web server 启动和 pending message recovery 可能存在短暂并行窗口；排查重启恢复问题时要按当前事实理解，而不是假设所有状态恢复都已经串行完成。

## 消息主链路

技术上，一次典型会话不是"前端发消息 -> 模型回消息"的直连，而是：

1. 渠道或 Web 把入站消息落到 `messages`
2. `chats` / `registered_groups` 同步更新路由与元数据
3. 主消息循环按 `lastTimestamp` 取全局新消息
4. `GroupQueue` 按会话串行化处理，避免同一会话并发执行多个 Agent
5. `processGroupMessages(...)` 根据 trigger、sender allowlist 和 committed cursor 选出真正要送给 Agent 的消息
6. `resolveAssistantRuntimeConfig(...)` 解析本次运行的 assistant、provider、访问策略和资源绑定
7. `runAgentProcess(...)` 拉起本地 Agent runtime
8. turn / approval / stream 事件经 Web channel 和 WebSocket 发往前端
9. 最终回复落 `messages`，结构化 turn 落 `assistant_turns`
10. committed cursor 提交，等待下一批消息

## Web 服务模型

`src/web/web-server.ts` 的设计重点不是承载业务状态，而是统一暴露控制面：

- 读接口集中在 `registerSystemReadRoutes(...)`
- 消息和会话读写集中在 conversation routes
- browser、repo review、stock analysis、knowledge、soul、live2d、auth、user 等各有独立 route/service
- `attachRealtimeWebSocketHandler(...)` 处理聊天增量事件
- `attachTerminalWebSocketHandler(...)` 处理 Web 终端

也就是说，路由文件主要承担 HTTP 合约、鉴权和依赖注入；核心运行语义仍然落在 `index.ts`、各 service 和 `db.ts`。

## 为什么要把 `assistant_turns` 和 `messages` 分开

这是当前系统设计里很重要的一点：

- `messages` 代表最终对话事实，适合会话列表、导出、检索和最终展示
- `assistant_turns` 代表执行过程事实，适合流式 UI、工具调用面板、审批展示和失败排障

如果只保存最终消息，会丢失：

- 工具调用过程
- 审批请求和审批结果
- 部分流式回复的中间态
- Agent 失败前已经产生的结构化执行轨迹

- `src/workflow/`：图形多智能体 Workflow Workbench 编排层（types、orchestrator、agent-adapter、event-bus、runner-profiles、project-detector、runner-profile-registry、artifacts、metrics、evaluation）
- `src/routes/`：46 个 HTTP route 模块
- `src/types/`：类型定义子模块（5 个文件）
- `web/`：前端（16 个主页面 + 子组件）
- `agent/runner/`：本地 Agent runtime
- `agent/skills/`：内置 Skills
- `skills-engine/`：Skills 安装与运行时引擎
- `scripts/`：维护、迁移与校验脚本
- `deploy/`：Kubernetes 部署清单
- `docs/`：中文现状文档
- `setup/`：安装与服务化辅助逻辑
- `groups/`：会话级工作区
- `data/`：上传、扩展、MCP 等运行时数据
- `store/messages.db`：主数据库（默认 SQLite，可切换 MySQL / PostgreSQL）

## 需要特别记住的事实

- 这是本地环境驱动的系统，不是无状态 SaaS
- 很多功能会直接接触文件系统、Git 仓库和本机脚本
- Agent 运行不是操作系统级沙箱
- Web API、浏览器、终端、Repo Review hooks、扩展安装和代码索引都可能触发高权限本地行为
- 文档中的 "conversation" 在实现层不等于单一数据库表；它是 `chats + registered_groups + sessions + router_state + messages + assistant_turns` 共同构成的运行时对象
- 数据库支持三种引擎（SQLite / MySQL / PostgreSQL），schema 变更须同步修改三套 DDL
