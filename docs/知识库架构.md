# 知识库架构

## 这份文档解决什么问题

NanoClaw 的知识库不是传统 RAG 流水线——不强制依赖嵌入模型或外部向量数据库。当前实现以**数据库原生全文搜索（FTS）为基础**，嵌入向量为可选增强，支持 SQLite、MySQL、PostgreSQL 三种方言。在 PostgreSQL 上可使用 jieba / zhparser 中文分词，中文检索效果显著优于默认 simple 分词。

这份文档描述当前仓库已落地的实现（含时序与关联增强），不描述未实现或未合并的设想路线。

## 时序与关联增强（L1/L2/L3）

知识库在 FTS + 可选向量混合检索之上，提供按知识库配置的**增强层级**（`enhancement_level`），分层引入元数据规则、异步 LLM 与 Wiki 维护能力；较低层级产出的数据在检索侧与较高层级隔离，避免未完成增强污染主检索。

### 三层增强模式概述

| 层级 | 配置值 | 能力概要 |
|------|--------|----------|
| **L1** | `metadata` | **规则化元数据提取**：发布日期推断（HTML meta `article:published_time` / `og:updated_time` / `datePublished` 优先，再回退到 URL/正文模式）、文档层级（URL 路径 + ZIP 内相对路径 → `doc_path` / `depth`）、**自动替代检测**（`superseded_by`）、检索侧**时序衰减加权**（与 `published_at`、半衰期配置配合）。 |
| **L2** | `wiki_lite` | 在 L1 基础上：**LLM 文档摘要**、**实体抽取**、**语义关联检测**（写入 `knowledge_doc_relations`）；候选筛选优先用嵌入相似度（无 embedding provider 时回退关键词重叠）；由异步任务驱动，状态字段见 `knowledge_documents.llm_status`。**手动触发**时会扫描当前 KB 全部 eligible 文档，并按**全局可配置的文档级并发池**推进。 |
| **L3** | `wiki_full` | 在 L2 基础上：**Wiki 页面自动生成**、**交叉引用维护**、**健康检查 / lint**、**Wiki FTS 搜索**（`knowledge_wiki_pages` 及索引）；手动触发 `POST .../llm-process` 时自动接续 wiki 维护，避免重试后摘要更新但 wiki 滞后；适合需要可浏览知识网络的场景。当前前端通过 `GET .../processing-status` 返回的**run 进度 + 活跃文档 + 文档树/概览进度条**观察处理状态。 |

### 新增数据表

| 表名 | 用途 |
|------|------|
| `knowledge_doc_relations` | 文档间语义关联（如 LLM 或规则检测到的相关、引用、替代关系等，具体语义以落库字段为准）。 |
| `knowledge_doc_summaries` | LLM 生成的文档摘要与抽取实体等派生内容，供检索加权与展示。 |
| `knowledge_wiki_pages` | Wiki 页面正文与元数据；含 **FTS 索引** 以支持 Wiki 范围全文检索。Karpathy 模式中的 `index.md` 入口页用 `page_type='overview'` 复用本表，每个 KB 至多一条。**人工修正锁**：列 `edited_by_human INT NOT NULL DEFAULT 0`、`edited_at VARCHAR(32)`，被人工编辑的页 `edited_by_human=1`，下一轮 `wiki-maintainer` 写入会跳过该页直到 `revert`。 |
| `knowledge_wiki_claims` | Wiki 页面“核心事实”的结构化证据层：按 page 保存 claim 文本、来源文档、证据 chunk 和置信度；详情 API 会连同证据摘要返回，检索侧优先用 claim 级证据。 |
| `knowledge_event_log` | KB 内部 append-only 事件流（`ingest` / `reindex` / `delete` / `llm_enhance` / `wiki_update` / `lint` / `query_backfill` / `supersede`）。对应 Karpathy 模式中的 `log.md`，既可供 UI 时间线，也作为 LLM lint/关联检测时的"近期变化"上下文。 |

### 扩展字段

**`knowledge_bases`**

- `enhancement_level`：增强层级（`none` / `metadata` / `wiki_lite` / `wiki_full` 等与实现对齐的枚举）。
- `embedding_provider_id`：该知识库绑定的 Embedding Provider；为空时表示只使用 FTS，不做向量检索。
- `llm_provider_id`：该知识库 LLM 增强使用的 Provider（可与全局默认解耦，直接使用 provider 默认模型）。
- `temporal_half_life_days`：时序衰减半衰期（天），与 `published_at` 等共同影响检索加权。
- `allow_query_backfill`：为 `1` 时允许通过 API / 内部接口将检索综合答案写入 `knowledge_wiki_pages`（`page_type='comparison'`），便于把 `knowledge_search` 的探索结果固化为 Wiki；默认 `0`。

**全局配置**

- `KB_LLM_CONCURRENCY`：整库 LLM / Wiki 重建的全局并发数（默认 `4`，建议 `1-16`），由系统配置与知识库界面共同展示/修改。

**`knowledge_documents`**

- `published_at`：发布/生效时间，用于时序衰减与排序。
- `superseded_by`：被哪条文档替代；检索可过滤已替代文档。
- `parent_doc_id`：父文档，与层级浏览一致。
- `doc_path` / `depth`：层级路径与深度，用于树形展示与**兄弟文档加权**。
- `llm_status`：LLM 增强流水线状态（pending / 处理中 / 完成 / 失败等与实现对齐）。

### 检索增强

- **已替代文档过滤**：依据 `superseded_by` 排除或降权已被替代的文档块。
- **时序衰减加权**：基于 `published_at` 与 KB 的 `temporal_half_life_days`，对较新内容给予有限提升（实现对齐的上限约为 **40% max boost**）。**多 KB 检索时按各 chunk 所属 KB 的半衰期分别加权**，不再取候选 KB 列表中第一个值。
- **兄弟文档加权**：同一父节点下的相邻/同级文档在融合分数时额外加权，便于成套说明被一起召回。
- **结构化 chunk 上下文**：Markdown 标题路径会写入 `heading_path` / `context_label`；检索命中 chunk 会附带同文档前后相邻 chunk。这样不额外引入 rerank 模型，也能缓解切块导致的语义断裂，并把上下文显式交给 Agent / LLM。
- **Wiki FTS + staleness**：在 `knowledge_wiki_pages` 上做全文检索，并结合页面与源文档更新时间做陈旧度（staleness）检查；判定为 stale 的页面**分数乘 0.5 后重新排序**，仍保留在结果中但排序权重明显下降，避免过时综合页压过更新的源文档。
- **Wiki 质量启发式重排**：Wiki 检索结果会结合 `page_type`、`source_doc_ids` 数量与正文长度做质量重排；`overview`、薄页面、单源弱页面默认低于稳定 entity/concept/synthesis 页。
- **`enhancement_level` 降级隔离**：未达到某层增强时，不混入该层才写入的索引字段或关联边，避免半成品污染主结果集。
- **LLM 输入抽样**：摘要阶段不再把所有 chunk 生硬拼接到 prompt，而是按文档结构抽取开头 / 中段 / 结尾代表片段，并附带 `filename` / `doc_path` / `published_at` 元信息，降低 prefill 成本并保留覆盖面。

### 后台维护任务

服务启动后每 5 分钟运行一次的轻量 sweep（见 `src/index.ts`）：

- **`recoverStuckLlmJobs`**：把 `processing` 超过 5 分钟未心跳的 LLM 任务回退为 `pending`；`pending` 超过 30 分钟无人处理的标记为 `failed`，保证崩溃恢复。
- **`rebuildOrphanParents`**：扫描 `parent_doc_id IS NULL AND doc_path LIKE '%/%'` 的"孤儿子文档"（多见于 URL BFS 爬取时子文档先于父文档入库），重新跑 `findParentDoc` 修复父链；单次 LIMIT 500 节流，避免大批量阻塞事件循环。
- **`regenerateAllDirtyOverviews`**：消费 `knowledge_bases.overview_dirty_at IS NOT NULL` 的 KB 列表（**持久化脏标记，崩溃不丢**），调用 `regenerateOverviewPage` 重建被改动 KB 的 overview 索引页并 `clearOverviewDirty` 清空标记。重建是规则化的（不调 LLM），内容未变化时跳过写库。
- **`pruneAllEventLogs`**：每个 KB 仅保留最近 1000 条事件；采用 `SELECT id ... ORDER BY created_at DESC LIMIT ? OFFSET keepRecent → DELETE WHERE id IN (...)` 的两步方案（用 id 删除避免 `created_at <` 时间戳范围的边界歧义），单次 sweep 每 KB 最多裁 2000 条，超出留给下次 sweep，避免长事务与超大占位符列表。
- **`autoLintOneOverdueKb`**：每轮 sweep 挑 1 个 `wiki_full + enabled` 且距上次 `lint` 事件超过 24 小时（或从未 lint）的 KB 跑 `lintWiki`，把 Karpathy "periodic lint" 落地为 tenant-friendly 的低频健康检查。
- **L2/L3 单 flight 锁**：`runLlmEnhancementChain` 使用进程内 `Map<docId, Promise>` 去重，并发触发同一文档的增强会复用同一个 in-flight Promise，防止重索引/手动重试时跑两次 LLM。
- **手动 LLM 并发池**：`POST /api/knowledge/bases/:id/llm-process` 使用文档级 worker pool（并发来自全局 `KB_LLM_CONCURRENCY`）扫描并处理指定范围文档；为避免大 backlog 在等待期间被恢复任务误判为超时，**未开始的文档不会在入队时统一写成 `pending`，而是在真正开始处理时直接进入 `processing`**。
- **KB 级 run registry**：手动 LLM 运行态会在进程内记录 `run_id / mode / total / queued / completed / failed / concurrency / started_at / finished_at`，供 `GET .../processing-status` 返回给前端展示真实进度，而不是仅靠文档 `llm_status` 推断。

### 迁移失败分级（MySQL / TiDB）

`src/db/schema-mysql.ts` 的 `safeMigrate` 不再**静默吞所有异常**：只对"已存在"类错误（`ER_TABLE_EXISTS_ERROR` / `ER_DUP_FIELDNAME` / `ER_DUP_KEYNAME` 等）放行，其他错误（权限不足 / 锁冲突 / 语法问题 / 引用缺失）会在 `logger.error` 后**直接抛出**，阻止服务以半迁移 schema 启动。

### 事件流（`knowledge_event_log`）

8 种事件类型在主流程关键节点 fire-and-forget 写入（任何写失败都只 warn，不影响主调用）：

| 事件 | 触发位置 | 典型 title |
|------|---------|------------|
| `ingest` | `pipeline.indexDocument` 索引成功 | `<filename> 入库（N chunks）` |
| `reindex` | `pipeline.reindexDocument` 重索引成功 | `<filename> 重新索引（N chunks）` |
| `delete` | `DELETE /api/knowledge/documents/:id` | `<filename> 已删除` |
| `llm_enhance` | `enhanceDocumentWithLlm` 完成 | `LLM 增强完成（wiki_lite \| wiki_full）` |
| `wiki_update` | `updateOrCreateWikiPages` 命中 ≥1 个页面 | `Wiki 更新 N 个页面` |
| `lint` | `lintWiki` 返回 | `Lint 完成（孤立 a / 过时 b / 缺失实体 c / 矛盾 d）` |
| `supersede` | `metadata-extractor.markSuperseded` | `<旧文档> → <新文档>` |
| `query_backfill` | `query-backfill.ts` / `POST .../wiki-pages/backfill`（及内部 `POST /internal/knowledge/backfill-wiki`） | `查询答案保存为 <title>` |

每次写入会同时把所属 `kbId` 加入 dirty 集合，触发下次 sweep 重建 overview 索引页。

| 表名 | 用途 | 关键字段 |
|------|------|---------|
| `knowledge_bases` | 知识库元数据 | `id`, `name`, `user_id`, `category`, `visibility`, `enabled`, `chunk_size`, `chunk_overlap`, `embedding_provider_id`, `llm_provider_id`, `allow_query_backfill`（是否允许查询结果回填 Wiki）, `overview_dirty_at`（持久化 overview 脏标记，NULL 表示无需重建） |
| `knowledge_documents` | 文档元数据 | `id`, `kb_id`, `filename`, `content_hash`, `source_url`（可选来源 URL）, `status`(`pending`/`indexing`/`indexed`/`failed`), `chunk_count` |
| `knowledge_chunks` | 文本分块 | `id`, `document_id`, `chunk_index`, `content`, `token_count`, `heading_path`, `context_label`, `prev_chunk_id`, `next_chunk_id`, `parent_chunk_id`, `chunk_type`, `search_vector`(PG tsvector) |
| `user_knowledge_bindings` | 用户级启用/禁用 | `id`, `user_id`, `kb_id`, `enabled` |
| `embedding_vectors` | 向量存储（共享表） | `id`, `owner_type='knowledge'`, `owner_id`=chunk.id, `embedding_provider_id`, `embedding`(BLOB), `dimensions`, `model_name` |

### 可见性与多租户

每个知识库有三个维度控制可见范围：

- **`user_id`**：创建者，`__system__` 表示系统级
- **`visibility`**：`private`（仅创建者）或 `shared`（全局可见）
- **`user_knowledge_bindings`**：用户级开关，覆盖默认 `enabled`

Agent 可用知识库 ID 的计算逻辑（`agent-runner-spawn.ts`）：

```
可用KB = 助手绑定的KB ∪ 用户启用的KB ∪ 全局共享且启用的KB
```

### FTS 索引结构

| 数据库 | FTS 机制 | 索引类型 | 分词配置 |
|--------|---------|---------|---------|
| SQLite | FTS5 虚拟表 `knowledge_chunks_fts` | BM25 排序 | `unicode61 remove_diacritics 2` |
| MySQL | `FULLTEXT INDEX ft_kb_content` 在 content 列 | `MATCH AGAINST` (BOOLEAN MODE) | 内置分词器 |
| PostgreSQL | `search_vector tsvector` 列 + GIN 索引 | `ts_rank` + `plainto_tsquery` | 自动检测: jieba > zhparser > simple |

## 数据流程

### 文档上传索引

```
1. POST /api/knowledge/bases/:id/documents
   ├── filename + content 传入
   │
2. pipeline.indexDocument(kbId, filename, content)
   ├── 校验 KB 存在
   ├── 创建 knowledge_documents 行 (status: pending)
   ├── status → indexing
   │
3. chunker.chunkText(content, {chunkSize, chunkOverlap})
   ├── 按段落与 Markdown 标题边界切分
   ├── 长段落按句子二次切分
   ├── 每块估算 token 数
   ├── 记录 heading_path / context_label / chunk_type
   │
4. insertKnowledgeChunks(chunkRecords)
   ├── 批量写入 knowledge_chunks
   ├── 写入 prev_chunk_id / next_chunk_id 作为相邻上下文指针
   │
5. ftsEngine.indexChunks(engine, chunkRecords)
   ├── SQLite: INSERT INTO knowledge_chunks_fts
   ├── MySQL: 自动索引 (FULLTEXT 列)
   ├── PG: UPDATE knowledge_chunks SET search_vector = to_tsvector('jieba', content)
   │
6. [可选] batchEmbedAndStore('knowledge', chunks, provider)
   ├── 调用嵌入 API
   ├── 写入 embedding_vectors (owner_type='knowledge')
   │
7. status → indexed, chunk_count 更新
```

### URL 导入

```
1. POST /api/knowledge/bases/:id/import-url
   ├── url, max_depth, max_pages
   │
2. url-importer.importFromUrl(opts)
   ├── validateUrl(): 协议校验 + SSRF 检查
   ├── fetchPage(): redirect: manual, 逐跳验证
   │   ├── Content-Type 检查 (text/html|text/plain)
   │   ├── 大小限制 (5MB)
   │   ├── 编码自适应 (charset 检测)
   ├── parseHtml(): cheerio 一次解析
   │   ├── 提取标题 (<title> / og:title)
   │   ├── 移除导航/脚注/脚本等噪声
   │   ├── 提取正文 (article > main > body)
   │   ├── 发现同域链接
   │
3. 每页正文 ≥ 50 字符 → pipeline.indexDocument()
4. depth < maxDepth → 发现的链接入队 (BFS)
```

### 混合检索

```
searchKnowledge(query, {kbIds, topK, minScore})
  │
  ├── 1. 确定搜索范围: 传入 kbIds 或 所有 enabled KB
  │
  ├── 2. FTS 搜索 (始终执行, 无外部依赖)
  │      ftsEngine.search(engine, query, {kbIds, limit: topK*3})
  │      ├── SQLite: FTS5 MATCH + bm25()
  │      ├── MySQL: MATCH AGAINST (BOOLEAN MODE)
  │      └── PG: plainto_tsquery('jieba') + ts_rank
  │
  ├── 3. 直接向量召回 (可选, 需要嵌入模型)
  │      在授权 KB 范围内扫描对应 provider 的 chunk embedding
  │      ├── 应用层扫描有硬上限，超过时保留 FTS 候选向量补分作为兜底，避免大库查询长时间阻塞
  │      ├── 自动跳过维度不匹配的旧向量（模型切换场景）
  │      ├── 余弦相似度 in-memory 计算
  │      └── 不再受 FTS 候选门控，语义同义问法可直接召回
  │
  ├── 4. FTS 候选向量补分
  │      对 FTS 命中的 chunk 再取 embedding 分数作为兼容兜底
  │
  ├── 5. 分数归一化 + RRF 辅助融合
  │      ├── SQLite BM25 取负 (低=好 → 高=好)
  │      ├── FTS / Vector 分源 min-max 归一化到 [0,1]
  │      ├── 双源: 0.45*FTS + 0.55*Vector
  │      ├── 单源: 按可用源动态归一，不惩罚 vector-only 命中
  │      └── 叠加 8% RRF 排名信号，稳定多路召回排序
  │
  ├── 6. 取 topK → 水合 chunk 详情 → 按 kbId 过滤
  │
  └── 7. 附加 heading_path / context_label / adjacentChunks → 返回给 API、统一 retrieval 与 Agent 工具
```

## 人工修正与 LLM 共存（PR Q-Edit）

### 设计目标

Karpathy LLM Wiki 模式默认假设：**人工随时可以编辑 wiki，编辑后 LLM 不再覆盖**。在此 PR 之前，NanoClaw 的 Wiki 完全由 `wiki-maintainer.ts` 自动重写，人工没有「编辑入口」也没有「锁」。本节描述补齐这一能力的最小落地。

### 数据契约

`knowledge_wiki_pages` 表新增两列：

| 列 | 含义 |
|----|------|
| `edited_by_human INT NOT NULL DEFAULT 0` | 1 表示「最后一次写是人工」，LLM 重写路径必须跳过 |
| `edited_at VARCHAR(32) NULL` | 最近一次人工编辑时间（ISO 字符串），`revert` 后清空 |

三方言迁移均采用 `ALTER TABLE ... ADD COLUMN`，旧库无需 dump 即可升级。

### 写入路径

```
人工编辑 (Web UI) ──► PUT /api/knowledge/wiki-pages/:id
                       ├─ 校验 title (≤255)、content (非空、≤512KB)、expected_version
                       ├─ 乐观锁：expected_version != current_version → 409
                       ├─ UPDATE: title/content/version+1/llm_model='human'
                       │          edited_by_human=1, edited_at=now, updated_at=now
                       ├─ updateWikiSearchVector(...)  (Wiki FTS 同步)
                       └─ safeAppendKbEvent(wiki_update, payload.mode='human_edit')

回滚 LLM 覆盖 ──► POST /api/knowledge/wiki-pages/:id/revert
                  ├─ UPDATE: edited_by_human=0, edited_at=NULL  (内容/version 不变)
                  └─ safeAppendKbEvent(wiki_update, payload.mode='revert_human_edit')

LLM 处理新文档 ──► updateWikiPage(page, ...)
                  └─ 入口短路：if (page.edited_by_human === 1) return;
```

### 不可编辑页

`page_type='overview'` 由 `overview-maintainer.ts` 规则化（无 LLM）自动生成，编辑后下一次 sweep 即被覆盖且无意义，PUT 端点直接拒绝（400）。

### Lint 报告字段

`WikiLintReport` 新增 `humanEditedPages: string[]`，列出当前 KB 中所有 `edited_by_human=1` 的页 id；事件流 `lint` 事件 payload 同步包含计数。便于运维快速识别"哪些页 LLM 已不再托管"。

### 与 Karpathy 模式的对齐

| 能力 | Karpathy 模式 | NanoClaw（PR Q-Edit 后） |
|------|---------------|------------------------|
| LLM 写 wiki | ✅ | ✅ `wiki-maintainer.ts` |
| 自动 lint | ✅ | ✅ `autoLintOneOverdueKb`（24h 间隔） |
| 索引页 (`index.md`) | ✅ | ✅ `page_type='overview'` |
| 事件流 (`log.md`) | ✅ | ✅ `knowledge_event_log` |
| **人工编辑保护** | ✅ | ✅ `edited_by_human` 锁 + 显式 revert |

## Agent 集成

### MCP 工具注册

知识库当前通过 5 个 MCP 工具暴露给 Agent，对齐 Karpathy LLM Wiki 模式中 agent 作为"wiki 维护副驾驶"的角色：

| 工具 | 内部端点 | 用途 |
|------|---------|------|
| `knowledge_list` | `GET /internal/knowledge/bases` | 列出用户可见 KB，每次会话开头先用 |
| `knowledge_search` | `POST /internal/knowledge/search` | FTS + 可选向量混合检索 |
| `knowledge_wiki_read` | `GET /internal/knowledge/wiki-pages/:id` | 读取单个 Wiki 页全文 |
| `knowledge_recent_events` | `GET /internal/knowledge/events` | 读 KB 近期事件流，回答"最近变化" |
| `knowledge_save_as_page` | `POST /internal/knowledge/backfill-wiki` | 把综合答案固化为 `comparison` wiki 页；需 KB `allow_query_backfill=1` |

Agent 行为契约见 [docs/knowledge-wiki-maintainer.md](./knowledge-wiki-maintainer.md)（LLM 纪律文档）。

这些工具**不会自动搜索知识库**——只有在以下条件满足时 Agent 才能调用：

1. **助手绑定了知识库** — 在助手配置中设置 `kbIds`
2. **用户启用了知识库** — 通过 `user_knowledge_bindings` 开关
3. **知识库全局共享** — `visibility='shared'` 且 `enabled=1`

注册链路：

```
agent-runner-spawn.ts
  ├── 计算 NANOCLAW_AVAILABLE_KB_IDS (JSON 数组)
  │   └── assistantKbIds ∪ userEnabledKbIds ∪ sharedKbIds
  ├── 写入 agent 进程环境变量
  │
ipc-mcp-stdio.ts (agent 进程内)
  ├── 读取 NANOCLAW_AVAILABLE_KB_IDS
  ├── 如果非空 → 注册 knowledge_search 工具
  ├── 调用时: 过滤 kb_ids 只允许可用列表内的
  └── POST ${INTERNAL_API_BASE}/internal/knowledge/search
      └── 鉴权: INTERNAL_API_TOKEN (已在 internal-api-auth 白名单)

codex-tools.ts / internal-memory-api.ts (agent runner 直接工具)
  ├── semantic_search 通过 internal knowledge search loopback 查询
  ├── 传入 NANOCLAW_CHAT_JID，使 assistant 绑定的私有 KB 可参与授权
  ├── 传入 NANOCLAW_AVAILABLE_KB_IDS 作为 kb_ids 白名单（存在但为空时 fail closed）
  └── NANOCLAW_USER_ID 缺失时不再回退 __system__，避免扩大 KB 可见范围
```

### 安全边界

- `NANOCLAW_AVAILABLE_KB_IDS` 是白名单，Agent 无法访问未授权的 KB
- `knowledge_search` 工具将用户传入的 `kb_ids` 与白名单取交集
- internal `POST /internal/knowledge/search` 也执行同样的交集语义；只要请求体显式包含 `kb_ids`，就只搜索 `kb_ids ∩ agentAccessibleKbIds`，空数组代表空 scope，不能回退到全部可见 KB
- `user_id` 是 internal knowledge loopback 的必填授权主体；runner 侧缺失 `NANOCLAW_USER_ID` 时必须 fail closed，不能用 `__system__` 兜底
- `chat_jid` 用于解析当前会话绑定的 Assistant，使 assistant-bound private KB 在该会话内可见；没有会话绑定时，私有 KB 仍只按创建者/用户绑定授权
- `knowledge_save_as_page` 受 KB `allow_query_backfill` 开关限制，且按 `(user_id, kb_id)` 每分钟 5 次滑动窗口限速
- 所有 internal 知识库端点共用 `INTERNAL_API_TOKEN` + 环回检查（见 `src/auth/internal-api-auth.ts`）

### 多副本语义（P1-3）

进程内状态不跨副本：

- **查询回填限速**（5 次/分）：多副本部署时每实例独立计数，真实上限 ≈ 副本数 × 5 次/分。由 `INTERNAL_API_TOKEN` 防外部滥用，内部限流为尽力而为；严格限速需迁到 Redis token bucket。
- **LLM 单 flight 锁**（`runLlmEnhancementChain` 内存 Map）：多副本并发触发同 `docId` 的 LLM 增强可能产生两次调用（后写胜出），**不会数据损坏**，仅是成本。严格单 flight 需迁到 DB advisory lock 或队列化。

这两条在单实例部署下都是严格的；多副本场景按规模决定是否升级为跨进程机制。

## PostgreSQL 分词配置

### 自动检测

启动时 `detectPgFtsConfig(engine)` 查询 `pg_ts_config` 系统表：

| 优先级 | 分词配置 | 说明 |
|--------|---------|------|
| 1 | `PG_FTS_CONFIG` 环境变量 | 手动覆盖，最高优先（需通过字符白名单 `[a-zA-Z0-9_]` + `pg_ts_config` 存在性校验） |
| 2 | `jieba` | pg_jieba 扩展，结巴分词 |
| 3 | `zhparser` | zhparser 扩展，SCWS 分词 |
| 4 | `simple` | PG 内置，空格分词（中文效果差） |

环境变量校验失败（字符非法或配置不存在）时，自动降级到优先级 2 继续检测，并输出 warn 日志。

### 影响范围

检测到的分词配置统一应用于：

- `knowledge_chunks.search_vector` 的索引和查询
- `memory_search_documents.search_vector` 的索引和查询（通用搜索引擎）
- `user_memories` 的 FTS 函数索引和查询

### 索引重建策略

系统启动时**仅检测** FTS 分词配置（`detectPgFtsConfig`），不自动执行任何数据重建。这避免了大表场景下启动阻塞和高资源占用。

当用户变更分词器（例如 simple → jieba）或安装新扩展后，需要手动触发重建：

- **前端**：知识库页面 Summary Strip 中的「重建 FTS」按钮
- **API**：`POST /api/knowledge/rebuild-fts`

重建操作包含三个步骤：

1. **`user_memories`** — 重建函数 GIN 索引（DDL）
2. **`memory_search_documents`** — 重算存量 tsvector 列（O(n)）
3. **`knowledge_chunks`** — 重算存量 tsvector 列（O(n)）

升级（simple → jieba）和降级（jieba → simple）走同一条路径。

> 如果未重建，存量数据仍使用旧分词器的 tsvector。新写入数据会自动使用当前配置，查询侧也使用当前配置，因此旧数据的召回率可能降低但不会出错。

### 查询方式差异

| 场景 | 旧实现 | 新实现 |
|------|--------|--------|
| 查询解析 | `to_tsquery('simple', '词1 & 词2')` — 手动拼接 | `plainto_tsquery('<cfg>', '原始查询文本')` — 分词器自动分词 |
| 索引写入 | `to_tsvector('simple', content)` | `to_tsvector('<cfg>', content)` |
| 效果 | 中文只能按空格切分，"人工智能"必须完整匹配 | jieba 自动分词，"人工智能"可匹配"人工"+"智能" |

## 前端页面

### KnowledgePage.tsx

知识库管理页面，功能包括：

- **KB 列表**：卡片式展示，按分类筛选，显示类别标签和可见性
- **创建 KB**：设置名称、描述、分类（通用/技术/业务/产品）、可见性（私有/共享）
- **文档上传**：支持文本文件和 `.zip` 压缩包批量上传（浏览器端 JSZip 解压）
- **URL 导入**：输入网页链接，设定爬取深度，自动抓取同域子页面
- **测试搜索**：在线测试 FTS 检索效果；有结果且已选中某个 KB 时可将当前结果摘要保存为 Wiki（`comparison` 页，需该 KB 开启「查询回填」）
- **用户启用/禁用**：每个 KB 可独立开关
- **状态概览**：紧凑的 summary strip 显示 KB/文档/分块数量和搜索模式；L2/L3 KB 通过文档列表 / 文档树中的 `llm_status` 徽标观察处理进度，必要时前端会轻量刷新列表而不是单独维护一条全局进度条。
- **关联图（L2+）**：`关联图` Tab 默认 **力图**（`react-force-graph-2d`），可切换到 **表格**；关系类型多选与最低置信度滑块在前端过滤，数据来自 `GET .../graph` 与 `GET .../relations`。默认仅显示**已处理节点**，未处理节点可手动打开；图内提供间距、缩放和重置视图控制。

### 安全限制

- **ZIP 上传**：最大 100MB 压缩包、单文件 10MB、最多 200 个文件
- **URL 导入**：SSRF 防护（内网/保留 IP 拦截）、逐跳重定向验证、最大 5MB/页

## 环境变量

| 变量 | 默认值 | 说明 |
|------|--------|------|
| `PG_FTS_CONFIG` | 自动检测 | PostgreSQL 分词配置名。设置后跳过自动检测 |
| `EMBEDDING_PROVIDER` | (空) | 旧版全局 Embedding 配置；知识库现已优先使用设置页中的 Embedding Provider 资源 |
| `EMBEDDING_MODEL` | (依赖 provider) | 旧版全局嵌入模型名称 |
| `EMBEDDING_API_KEY` | (空) | 旧版全局嵌入 API 密钥 |
| `EMBEDDING_BASE_URL` | (空) | 旧版全局嵌入 API 地址 |
