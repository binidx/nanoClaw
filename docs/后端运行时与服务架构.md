# 后端运行时与服务架构

## 这份文档解决什么问题

现有功能文档按业务主题拆分，但如果要理解 NanoClaw 后端为什么能把聊天、任务、Repo Review、memory、知识库、灵魂、股票分析和浏览器放在同一进程里，需要先看运行时主链路。这份文档只讲后端的职责边界、状态模型和执行路径。

## 模块分层

### 编排层

- `src/index.ts`
  主运行时入口和启动生命周期。
- `src/runtime/runtime-state.ts`
  共享运行时状态绑定（`registeredGroups`、`sessions`、游标等）。
- `src/runtime/runtime-dispatch.ts`
  消息循环和消息分发逻辑。
- `src/runtime/runtime-channels.ts`
  渠道连接和管理。
- `src/runtime/runtime-persistence.ts`
  turn 持久化、实时事件广播和回复落库。

### 控制面

- `src/web/web-server.ts`
  负责 Express、WebSocket、登录态、origin 校验、静态资源和 route 装配。
- `src/routes/*`（46 个模块）
  负责 API 合约、参数校验、鉴权和依赖注入，不应该被视为业务核心。
  当前 route 模块包括：`admin-settings-routes`、`assistant-routes`、`auth-routes`、`browser-routes`、`channel-instance-routes`、`code-search-routes`、`conversation-admin-routes`、`conversation-memory-routes`、`conversation-message-routes`、`internal-memory-routes`、`knowledge-routes`、`live2d-routes`、`memory-identity-routes`、`repo-review-routes`、`runtime-customization-routes`、`soul-routes`、`stock-analysis-routes`、`system-read-routes`、`task-session-routes`、`user-provider-routes`、`user-routes`、`whatsapp-webhook-routes`。

### 持久化层

- `src/db.ts`
  Barrel re-export，实际实现位于 `src/db/` 下 32 个子模块。
- `src/db/sql-adapters.ts`
  SQL 方言适配（`adaptSql`、`PG_TABLE_PK_COLUMNS`、`PG_TABLE_IGNORE_CONFLICT_COLUMNS`）。
- `src/db/schema-sqlite.ts` / `schema-mysql.ts` / `schema-postgres.ts`
  三套 DDL schema。
- `src/db/init.ts`
  Schema 创建和迁移。
- `src/db/sql-utils.ts`
  SQL 工具函数。
- `src/db/engine-access.ts`
  数据库引擎访问桥接。
- `src/db/conversations.ts` / `tasks.ts` / `sessions.ts` / `assistants.ts` / `config.ts` / `memory.ts` / `review.ts` / `soul.ts` / `live2d.ts` / `files.ts` / `users.ts` / `stock-analysis.ts`
  按领域拆分的 21 个 CRUD 模块。

### 数据库引擎抽象层

- `src/database/*`（8 个子模块）
  引擎接口、方言检测、工厂、三种引擎实现和搜索引擎适配。
- `src/database/engine.ts`
  统一的数据库引擎接口定义。
- `src/database/dialect.ts`
  方言检测与切换逻辑。
- `src/database/factory.ts`
  根据配置创建对应数据库引擎实例。
- `src/database/sqlite-engine.ts` / `mysql-engine.ts` / `postgres-engine.ts`
  三种数据库引擎的具体实现。
- `src/database/search-engine.ts`
  搜索引擎适配（全文检索等）。

### 执行层

- `src/agent/agent-runner.ts`
  Barrel 入口。把后端上下文转换为可执行的本地 Agent 子进程。
- `src/agent/agent-runner-types.ts` / `agent-runner-mounts.ts` / `agent-runner-spawn.ts` / `agent-runner-process.ts` / `agent-runner-snapshots.ts`
  类型、挂载解析、进程启动、输出处理、快照 I/O。

  被启动的本地 runtime 目录。

### 资源解析层

## 启动顺序

`main()` 的启动顺序决定了很多运维语义：

1. 初始化数据库和 schema（根据配置选择 SQLite / MySQL / PostgreSQL 引擎）
2. 应用运行期配置，例如 `ALLOW_INSECURE_TLS`
3. 等待 `loadState()` 恢复 `router_state`、`sessions`、`registered_groups`
4. 恢复 pending messages
5. 恢复孤儿 subagent runtime
6. 连接所有已启用渠道
7. 启动 Repo Review auto sync / digest loop
8. 启动 task scheduler
9. 启动 context compaction、trash cleanup、IM AI、memory maintenance、soul consolidation、knowledge maintenance 等后台循环
10. 启动 IPC watcher
10. 启动 Web server 和 WebSocket
11. 扫描待恢复消息
12. 启动主消息轮询循环

当前实现没有把 `loadState()` 和 pending cursor timestamp reconcile 作为强同步启动屏障；它们可能与后续 channel/web/message recovery 并行。因此重启恢复类问题需要同时检查内存状态、持久化状态和启动日志时序。

设计上把这些环节显式排开，是为了让"渠道、控制面、后台任务、消息消费"都能独立恢复，而不是把整个系统绑定成一个巨大同步启动事务。

## 状态模型

### 数据库中的事实状态

- `chats`
- `messages`
- `assistant_turns`
- `context_entries`
- `scheduled_tasks`
- `task_run_logs`
- `router_state`
- `sessions`
- `registered_groups`

这些表用于恢复、查询、列表聚合和跨模块共享。

### 进程内热状态

- `registeredGroups`
- `sessions`
- `lastTimestamp`
- `lastAgentTimestamp`
- `pendingAgentTimestamp`
- `pendingUploadedFiles`

这些状态追求低延迟和执行中间态，不适合每一步都做重持久化。

### 为什么不是"全持久化状态机"

- 入站消息和流式 turn 事件频率高
- 同一会话必须串行，但全局需要并行
- 需要在失败时保留可见输出，同时允许未确认部分重试

所以系统采用"关键游标持久化 + 中间态内存化 + 事实结果落库"的折中方案。

## 消息消费与游标语义

### 两级游标

- `lastTimestamp`
  全局轮询水位，只表示"消息循环见过哪些消息"
- `lastAgentTimestamp`
  会话级 committed cursor，只表示"这个会话稳定消费到哪里"
- `pendingAgentTimestamp`
  会话级 pending cursor，表示"消息已被取出，但结果是否稳定可见尚未确认"

### 为什么需要 pending cursor

如果只有 committed cursor，运行中崩溃时系统无法判断这批消息到底：

- 完全没处理
- 处理了但没发出去
- 发出去了但没落库

有了 pending cursor，系统可以在恢复时根据数据库里是否已存在 bot reply 来决定提交还是回滚。

### 恢复策略

`reconcilePersistedPendingAgentTimestamps()` 的语义是：

- 如果某个 pending 时间点之后已经有 bot reply，则把它补提交为 committed
- 如果没有看到持久化 bot reply，则清空 pending，让消息重新进入待处理

这是当前避免"重复消费"和"跳过消息"的核心机制之一。

## 执行链路

一次正常执行路径如下：

1. 渠道把消息写入 `messages`
2. 主循环用 `getNewMessages(...)` 扫描全局增量
3. 按 `chat_jid` 聚合后交给 `dispatchPendingMessages(...)`
4. `processGroupMessages(...)` 再按会话 committed cursor 取真正未处理的消息
5. 根据 trigger、sender allowlist 和会话配置筛选输入
6. 写入 `pendingAgentTimestamp`
7. 调用 `runAgent(...)`
8. `runAgent(...)` 刷新 task/group 快照，解析 assistant runtime，拉起 `runAgentProcess(...)`
9. turn / stream / approval 事件通过 Web channel 广播
10. 最终消息写入 `messages`，turn 快照写入 `assistant_turns`
11. 提交 committed cursor

## 为什么 `GroupQueue` 必不可少

NanoClaw 允许不同会话并行执行，但同一会话必须串行，否则会出现：

- 会话 session 被并发污染
- 回复顺序颠倒
- pending cursor 被后一次运行覆盖
- 上传文件和审批上下文绑定错位

`GroupQueue` 的设计目的就是把"全局可并行、单会话必串行"这个约束固化到运行时。

## Web 服务为什么是"装配层"

`createWebServer(...)` 负责：

- 创建 Express 和 HTTP server
- 注册 conversation、task、browser、repo review、stock analysis、knowledge、soul、live2d、auth、user、runtime customization 等 46 个 route 模块
- 建立 `/ws` 和终端 WebSocket
- 在 `close` 时清理 browser service
- 处理 `EADDRINUSE` 这类控制面错误

但它不直接持有聊天游标、任务队列或 Agent 状态。这些核心状态仍在 `src/index.ts` 和相关 service 中。

## 典型设计取舍

### 1. `messages` 与 `assistant_turns` 分层

优点：

- 最终对话事实和执行过程都可回放
- 前端可以展示工具调用和审批中间态
- 失败排障时不会只剩最终一段文本

### 2. `registered_groups` 与 `chats` 分层

优点：

- `chats` 负责用户可见的会话元数据
- `registered_groups` 负责运行时路由、folder、trigger、assistant 绑定
- 会话名刷新和运行时路由变更互不污染

### 3. IPC/快照文件而非直接共享内存

优点：

- 子进程运行器边界更清晰
- 重启和孤儿 runtime 恢复更容易做
- 对 task/group 可见性的控制更明确

### 4. 多数据库引擎支持

`src/database/` 抽象层的设计使系统可以在 SQLite、MySQL 和 PostgreSQL 之间切换，而不影响上层业务逻辑。SQL 方言差异通过 `src/db/sql-adapters.ts` 的 `adaptSql` 自动转换。

## 运维时最值得关注的点

- `nanoclaw.pid` / `nanoclaw.port` 是否存在且与当前进程匹配
- `/api/status` 是否能看到 channels、agents、memory 和 subagents 状态
- `router_state` 是否出现异常 pending cursor
- `registered_groups` 是否和实际会话一致
- 是否存在孤儿 subagent runtime 被启动期恢复
- Web 端口冲突时，控制面会降级不可用，但后台进程不一定立即退出

## 容易误解的地方

- "会话"不是单表对象，而是多表加热状态拼出来的运行时概念
- `agent/runner/` 不是后端 orchestrator，本体 orchestrator 在 `src/index.ts`
- Web server 不拥有核心业务状态，它只是控制面
- `router_state` 不是普通配置表，它是恢复语义的一部分
- 很多大文件已拆分为 barrel + 子模块结构，导入路径保持向后兼容（如 `import { ... } from './db.js'` 仍有效），但新增导出应加到对应子模块
- `src/database/` 和 `src/db/` 是两层：前者是引擎抽象，后者是业务 CRUD
