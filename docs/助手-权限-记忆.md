# 助手、权限与记忆

## Assistant 的角色

Assistant 是会话运行时的配置载体，不是单纯的人设卡片。它决定一次会话真正如何执行，可绑定：

- Provider / Model
- Skills
- MCP Servers
- 访问策略
- 规则模式与附加提示词
- 项目根目录覆盖

不同会话可以绑定不同 Assistant，因此系统天然支持按工作流隔离 runtime。

## 多用户隔离

助手表增加了 `user_id` 和 `visibility` 列：

- `user_id`：创建者 ID，默认 `__system__`
- `visibility`：`private`（仅创建者可见）或 `shared`（所有用户可见）

列表查询按用户过滤：`WHERE user_id = ? OR user_id = '__system__' OR visibility = 'shared'`。创建者可以通过 `PUT /api/assistants/:id/visibility` 切换可见性。只有助手所有者（或系统用户）可以修改和删除助手。

## Assistant 运行时解析

后端会把 Assistant 解析成真正的运行时覆盖项，而不是原样把表单 JSON 传给 Agent。当前重要输出包括：

- provider / model override
- system prompt + extra instructions 组成的运行时附加指令
- managed skill ids
- managed MCP server bindings 与关联 secret env
- access policy override
- project root override
- rule mode

## Prompt 配置中心

系统现在提供统一的 Prompt 配置中心，而不是只依赖后端硬编码字符串。

当前能力：

- 可在前端设置页查看和编辑 Prompt 定义
- 支持 `system default` 与 `user override` 两层配置
- 运行时优先级为：`user override -> system default -> 现有内置 fallback`
- 配置修改后无需重启，后续请求直接生效
- 支持 Prompt Trace，可查看某次真实请求里 system prompt、会话 prompt、以及分段装配结果

这套中心的目标不是“多一页表单”，而是把原本黑盒的运行时提示词链路显式化。

## 聊天 Prompt 装配

聊天主链路的提示词不再只靠零散字符串拼接来理解。当前可以明确看到至少这几层：

1. 会话 user prompt
   由 `assembleAgentContext(...)` 生成，包含 recent context、memory recall、压缩摘要等上下文片段。
2. Assistant instructions append
   由 Assistant persona、assistant system prompt、extra instructions、会话级 custom instructions 合成。
3. Soul system prompt
   由 Soul 包装层 + 用户人格字段 + 行为规则 + 额外指令 + 记忆/洞察共同组成。
4. Companion mode hint
   当会话模式是陪伴模式时，追加专门的语气/长度控制提示。

这些分段会在 trace 里保留，便于回答“这一轮到底给 AI 传了什么”。

如果 Assistant 被删除或停用，某些执行路径会直接拒绝继续运行，而不是静默降级。

知识库不会自动进入普通会话 prompt。Assistant 绑定知识库后，Agent 仍通过 knowledge MCP 工具或 runner `semantic_search` 按需检索。internal 知识库授权口径是 `用户可见 KB ∪ 用户启用 KB ∪ shared KB ∪ 当前 chat_jid 绑定 Assistant 的 kbIds`；assistant-bound private KB 只在能从 `chat_jid` 解析到启用 Assistant 时加入可见范围。

## 助手页为什么是"工作台"

当前助手页不只是 CRUD，它还承担：

- 助手目录与状态总览
- 编辑器表单
- 资源抽屉
- 权限抽屉
- 私有认证管理
- 最近会话/运行信号
- 从助手上下文发起创建对话

资源和认证没有直接塞进大表单，而是分抽屉异步加载，这是为了避免一个页面同时承载过多远程状态和敏感信息。

## 访问策略

当前访问模式：

- `allowall`
- `allowlist`
- `readonly`

访问策略存在明确继承链：

1. 全局默认
2. Assistant 默认
3. 当前会话覆盖

聊天页的 access dialog 还会额外展示运行期临时授权，因此"最终能访问哪些目录"不一定只看持久化配置。

## 为什么访问策略是运行时核心而不是装饰项

访问策略直接决定 Agent 能触达哪些本地路径，也会影响：

- 终端能否进入某些目录
- 浏览器和 Repo Review 触发高权限动作时的安全边界
- 工作区映射如何暴露给 Agent 子进程

因此它和 Assistant、终端、浏览器、Repo Review 必须一起看，不能只把它理解为一个 UI 下拉框。

## 项目根目录与目录映射

当前实现里，Assistant access policy 的首个目录常被用作 `projectRootOverride`。前端配置的是 host path，但 UI 会进一步推导主目录和附加目录如何映射进 runtime。

这样设计的原因是：

- 对 Agent 来说，项目根目录需要是明确的工作上下文
- 对用户来说，仍希望用宿主机路径直接配置权限

## 发送者与会话边界

除目录访问外，系统还维护 sender trust 与 allowlist 逻辑。渠道消息不是默认全都可信，尤其当会话能触发本地文件系统、终端、Repo Review 或浏览器操作时，发送者边界就是安全边界的一部分。

## 用户与权限（RBAC）

系统实现了基于角色的访问控制，与 Assistant 访问策略互为补充：

- 访问策略控制 Agent 对本地目录的触达范围（运行时边界）
- RBAC 控制用户对 API 的访问权限（控制面边界）

RBAC 涉及的表：`users`、`roles`、`permissions`、`role_permissions`、`user_roles`、`auth_sessions`。

## Memory 系统

NanoClaw 的 Memory 不只是聊天记录回看，它包含：

- 身份画像与别名
- 会话到 person 的绑定
- group / global 两级 scope
- 文档索引与检索
- recall 记录
- 上下文装配
- 自动压缩与记忆提升

当前前端和后端都会把 Memory 当作"长期上下文层"，而不是某条消息的注释系统。

## Memory 的整体分层

当前实现更接近一套分层记忆运行时，而不是"把历史消息多存几份"：

- `context_entries`
  会话上下文层。记录用户消息、助手消息、session memory、memory recall、压缩摘要等可参与 prompt 装配的片段。
- `memory_documents`
  durable memory 层。承载 group memory、global memory、identity memory，并进入索引检索链路。支持 hybrid 检索（BM25 + vector embedding 混合打分）。
- `conversation_identity_bindings`
  会话到 person 的绑定层。决定某个 conversation 是否能读到对应 identity memory。
- `context_compactions`
  长历史压缩层。把较旧聊天片段变成摘要，避免 prompt 无限回放原文。
- `memory_*_stats`
  观测层。记录配置、生效状态、搜索、新鲜度、promotion、prompt 预算等指标快照。

这几个层级的职责不同：

- `context_entries` 解决"当前这轮模型该看到什么"
- `memory_documents` 解决"哪些信息值得长期保存并可检索"
- identity binding 解决"这是谁的长期信息"
- compaction 解决"长对话如何不把 prompt 撑爆"

## 灵魂系统

灵魂系统是记忆系统的上层抽象，负责对用户画像做长期沉淀与洞察：

现在 Soul 相关提示词也进入了 Prompt 配置中心。你可以分别看到：

- Soul 包装提示词
- 人格核心描述 section
- 行为准则 section
- 额外指令 section
- 最终注入到会话 system prompt 的完整 Soul 内容

这意味着 Soul 不再是黑盒字段集合，而是可追踪、可调整、可验证的运行时 prompt 片段。

- `user_souls`：用户 Soul 记录
- `user_soul_memories`：Soul 关联的记忆条目
- `user_memories` / `user_memory_observations`：用户记忆与观测事件（bi-temporal）
- `persona_insights`：基于 LLM 分析生成的人格洞察
- `memory_consolidation_log` / `memory_extraction_log`：记忆合并与提取日志

灵魂系统依赖 Memory 和 Identity 基础设施，通过后台 "Soul Consolidation" 调度（promote、insights、merge、prune）实现长期用户画像的自动沉淀。

## 知识库

知识库为会话提供长期知识上下文，与 Memory 互为补充：

- Memory 侧重用户交互中产生的动态记忆
- 知识库侧重预置文档中的静态知识

涉及的表：`knowledge_bases`、`knowledge_documents`、`knowledge_chunks`、`embedding_vectors`。

向量 Embedding 支持多引擎：OpenAI、智谱、Ollama（`src/embedding/` 层）。

Agent loopback 合约：

- runner 必须随 internal knowledge search 传 `user_id`，缺失时 fail closed，不能降级为 `__system__`。
- runner 会传 `chat_jid`，后端据此解析 Assistant 绑定的 private KB。
- `NANOCLAW_AVAILABLE_KB_IDS` / 请求体 `kb_ids` 是 scope 白名单；显式空数组表示不允许搜索任何 KB，不能回退到全部可见 KB。

## 当前可见能力

- `api/memory/identities*`
  身份管理与绑定
- `internal/memory/*`
  recall、索引、搜索与观测
- 会话运行时里的记忆注入与上下文预算控制
- 压缩与提升相关的后台调度
- 知识库 CRUD 与向量检索（`knowledge-routes`）
- 灵魂与人格洞察管理（`soul-routes`）

## 运行时边界

Memory 目前有几个很重要的边界，文档里最好直接记住：

- 它不是"全量聊天历史自动注入"
  进入 prompt 的只是预算内、去重后、按 source_type 过滤过的上下文片段。
- 它不是"所有记忆都来自数据库"
  durable memory 同时依赖数据库、group/global memory markdown 文件、identity 文档物化和索引同步。
- 它不是"写入即刻可搜"
  文件索引和新鲜度检查存在后台同步与补救刷新，搜索命中不是强实时。
- 它不是"所有自动分类都可靠"
  auto-promotion 依赖规则和高信号表达，擅长抓偏好、身份、长期约束，不等于通用语义理解。
- 它不是"session_only 就不落库"
  session memory 仍会进入 `context_entries`，只是语义上不写入 durable memory 文档。

## 使用建议

- 把 identity 视为"人"的长期信息，而不是某一次聊天标签
- group memory 适合团队/会话上下文
- global memory 适合跨会话长期知识
- 知识库适合预置文档和静态知识
- 灵魂系统适合长期用户画像沉淀
- 遇到记忆检索不准时，先检查 scope、索引状态和文件是否同步

## 限制与风险

- 索引同步不是完全实时
- 记忆搜索结果受 scope 和路径引用新鲜度影响
- 记忆写入和自动压缩都会改变本地状态
- auto-promotion 更适合高信号、长期性表达，不保证正确理解隐含语义
- global / identity / group 不只是展示分类，它们决定写入位置、检索范围和 owner 语义
- 如果把 Assistant、访问策略和 Memory 的边界理解错，容易误判为"模型回复异常"，实际上是上下文装配结果发生了变化
- 知识库向量检索依赖 Embedding 引擎的可用性和配置正确性
